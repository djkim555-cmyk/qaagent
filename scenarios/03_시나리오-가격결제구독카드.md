## ⚠️ 착수 전 필독 — 이 묶음에만 있는 3가지 전제

### 전제 1. 결제 화면은 "정상 클릭 경로로 도달 불가"다 (RSK-002, open blocker)
실사이트 실증(`03_실사이트-실물지도.md` §5-2)에서 확인된 사실:
- `/pricing`의 유료 플랜 **"구매하기" 3개 전부** href가 `/login?next=/my/sites` → **로그인 상태에서도** 최종 착지가 `/my/sites`(결제 화면 아님).
- 사이트 카드의 **"플랜 업그레이드"·"구독 취소하기"는 `is-disabled`**(비활성).
- 즉 앱 어디에도 `/purchase`로 가는 링크가 없다(`grep` 참조 0건).

**그래서 이 묶음의 결제 계열 태스크는 도달 경로를 반드시 둘로 나눠 쓴다.**

| 경로 | 무엇인가 | 결과 해석 |
|---|---|---|
| **경로 ①(정상 클릭)** | 사용자가 화면의 버튼·링크만 써서 목적지에 가려는 시도 | **막히는 것이 정상 관측치다.** 막혔다면 **RSK-002 재현 성공**이지 테스터의 실수가 아니다. 리포트에 "경로① 실패 = blocker 재현"으로 기록한다 |
| **경로 ②(URL 직접 진입)** | 시나리오가 지정한 주소로 직접 진입해 화면 내부를 검증 | 화면 안쪽 UI·검증 문구를 보기 위한 **우회 수단**. "사용자가 실제로 이렇게 도달한다"는 뜻이 아니다 |

> 페르소나는 **경로 ①을 먼저 자기 방식대로 충분히 시도**한 뒤(여기서 겪은 혼란·체감이 핵심 데이터다), 그다음 경로 ②로 넘어간다. 경로 ①을 건너뛰고 URL부터 치면 **이 묶음의 가장 중요한 발견을 통째로 잃는다.**

> ✅ **리드 판정(00_INDEX §5 B-3) — 우회 진입 "조건부 허용"**: 경로 ②(URL 직접 진입)는 **허용되나 순서가 강제**된다.
> - **경로 ①(정상 클릭)을 먼저 수행하고 그 결과를 기록한 뒤에만** 경로 ②로 넘어간다. 경로 ① 미수행 상태의 경로 ② 결과는 **무효**로 처리한다.
> - 경로 ① 실패 = **"RSK-002 재현 성공"**(테스터 실수 아님).
> - 경로 ② 결과에는 반드시 **"우회 진입 — 사용자가 실제로 이렇게 도달한다는 뜻이 아님"**을 병기한다.
> - 적용 태스크: **T3 · T5 · T6 · T8 · T9 · T10 · T11**(URL 직접 진입을 쓰는 전 태스크).

### 전제 2. "이미 결제한 사용자" 상태의 계정이 하나도 없다
검수 계정 10개 전수 실측(`03_실사이트-실물지도.md` §3):

| 상태 | 보유 계정 수 |
|---|---:|
| 사이트 보유 | **1개**(도탑 — 무료 FREE, `planState=pending`, 배지 "개설 중") |
| 유료 플랜 구독 | **0개** |
| 카드 등록 | **0개** |
| 결제 내역 | **0건** |
| 구독 레코드 | **0건**(`GET /api/subscriptions` → `items:[]`) |

**그래서 "이미 결제한 사용자" 전제 화면(구독 정보·업그레이드 견적·연장 견적·미납 청구서·결제 내역 표·구독 취소 확인 모달)은 실데이터로 도달할 수 없다.** 이 경우 결과를 **세 갈래로 갈라 적는다**:

| 기록 | 언제 쓰나 |
|---|---|
| **정상(빈/비활성 상태 검증됨)** | 화면이 설계된 empty·disabled 분기를 문서대로 보여줬다 (예: "이미 정상 처리되었거나 재시도 대상이 아닌 상태입니다") |
| **`[미확인]`(데이터 부재로 도달 불가)** | 데이터가 있어야만 보이는 UI를 못 봤다. **"정상"으로도 "결함"으로도 단정하지 않는다** |
| **결함(증거 있음)** | 빈/비활성 상태 자체가 문서·문구와 어긋난다 (예: 데이터가 없는데 "불러오지 못했어요"라고 말한다) |

### 전제 3. 개발 단계 표식은 결함이 아니다 (오탐 방지)
실물 화면에 **의도적으로** 노출된 표식 6종 — `사용량 미연동` / `저장 미구현` / `EP 미비` / `스테이징(실 카드인증 비활성)` / `결제 전 예상치` / `⚠ 임시 검수용 로그인`.
→ 이것을 "버그"로 올리면 오탐이다. 대신 **"이 표식이 사용자에게 어떻게 읽히는가(신뢰도에 어떤 영향인가)"**를 관찰 포인트로 적는다.

## 1. 서비스 개요

- **서비스명**: 쏠쏠(solsol) 브랜드사이트
- **한 줄 설명**: 크리에이터가 자기 이름의 온라인 강의 사이트를 개설하고, 요금제를 골라 구독·결제하며, 결제수단·계정을 스스로 관리하는 셀프서비스 사이트
- **대상 사용자**: 유튜브·SNS로 이미 팬을 모은 크리에이터 및 소규모 교육 사업자. 결제·구독 관리에 익숙한 사람부터 "카드 등록"이라는 말 자체가 부담스러운 사람까지 폭이 넓다
- **핵심 가치 제안**: "내 강의 비즈니스를 위한 사이트를, 요금제 하나 고르는 것만으로 시작하고 유지한다"
- **이 묶음이 검증하는 것**: 그 약속 중 **돈이 오가는 절반** — 요금제를 이해하고(가격), 유료로 올리고(구매·업그레이드·연장), 실패를 복구하고(즉시결제), 그만두고(구독취소), 결제수단과 계정을 관리하는(카드·계정) 전 구간

## 2. 테스트 환경

- **대상 URL**: `https://solsol-brand.pages.dev/` — ⚠️ **`config/target.json`의 `baseUrl`과 일치해야 하나, 2026-07-28 시점 실제 파일은 다른 서비스(`http://localhost:8000` · "구글 파트너 정산")를 가리킨다**(00_INDEX §5 B-1, 미해결 블로커). **실행 전 solsol-brand 전용 프로필 설정이 선행되어야 하며**, 설정 전 실행하면 전 페르소나가 엉뚱한 앱을 테스트한다. **"일치한다"고 단정하지 말고 착수 시 실제 `baseUrl`을 확인해 기록한다.**
- **접근 방식**: 공개 + **로그인 필요**(이 묶음의 대부분이 `/my/**` 보호 구간). 비로그인으로 보호 URL 진입 시 `/login?next=<원경로>`로 리다이렉트되는 것이 정상
- **테스트 계정**: `config/target.json` 참조. 로그인 화면 하단의 **검수용 로그인 버튼**으로 진입한다. **자격증명(계정·비밀번호)을 리포트·로그에 절대 기재하지 않는다**(정지선 #11 — "검수 계정"으로만 지칭)
- **권장 계정 배정**(실물지도 §3-A):

| 태스크 성격 | 권장 계정 | 이유 |
|---|---|---|
| 가격 탐색·구매 시도·구매 화면 진입 | **도탑** | 사이트를 가진 유일한 계정 → `/purchase?siteId=` 진입에 필요한 대상 사이트가 있다 |
| 사이트 카드 버튼 비활성 재현·업그레이드/취소 진입 | **도탑** | 사이트 카드 UI를 볼 수 있는 유일 계정 |
| 카드 등록·계정 관리·결제 이메일 변경 | **뿌꾸 / 윤희** | 카드 0장 상태에서 등록 플로우 전체를 밟음 |
| 결제 내역 빈 상태·필터·키보드 조작 | **검수 리뷰어 / 디제 / 겸겸 / 미니** | 결제 0건 빈 상태 + 필터 UI만 검증(데이터 불필요) |

- **지원 뷰포트**: **모바일 390×844 / PC 1440×900** — 페르소나 기기에 맞춰 적용. 모바일 페르소나는 **결제 화면의 2열(플랜 요약 ↔ 결제 카드) 레이아웃이 세로로 어떻게 접히는지**, **로그인 후에도 헤더 최상단을 차지하는 "무료로 시작하기" CTA가 혼동을 주는지**를 반드시 함께 기록한다

## 3. 사전 조건 (Preconditions)

1. 브라우저 자동화 도구가 연결돼 있다. 연결되지 않았다면 **모든 기능 판단은 `[추정]`**으로 표기한다.
2. 페르소나는 **검수 계정으로 로그인**한 상태에서 시작한다(T1·T2의 비로그인 관찰 파트 제외).
3. 테스트 시작 시점의 계정 상태를 먼저 확인해 기록한다 — **사이트 수 / 카드 수 / 결제 내역 수 / 구독 수**. 이 4개 값이 이후 모든 `[미확인]` 판정의 근거가 된다.
4. **여러 페르소나가 같은 계정을 동시에 쓰지 않는다**(카드 등록·삭제가 서로의 상태를 오염시킨다).
   - ⚠️ **실행 가능성 제약(검수 지적 B-5)**: **페르소나 20인 vs 검수 계정 10개**라 1:1 배타 배정이 원리적으로 불가능하다. 따라서 이 조건은 **"동시 사용 금지"**로 읽고 아래 규칙으로 운용한다.
   - **(a) 웨이브 분할**: 계정 1개는 **한 시점에 페르소나 1명만** 점유한다. 묶음 ③은 **10인 이내 웨이브**로 나눠 실행하고, 웨이브 전환 시 계정을 회수·재배정한다(00_INDEX §4-0 권고).
   - **(b) 상태 변경 여부로 공유 가능성을 가른다**: **읽기 전용 태스크**(T1·T2·T5·T6·T22·T23·T24·T25~T27)는 같은 계정을 **시간대를 갈라** 순차 공유해도 된다. **상태를 바꾸는 태스크**(T4 카드 등록 · T13 저장 · T19 이메일 변경 · T14~T18 모달)는 **계정 전담(배타)**이며 공유 금지.
   - **(c) 카드 계열 전담**: B-4 완화 대상 지정 계정 1개는 **페르소나 1인이 전담**한다(§ T4 참조). 다른 페르소나가 이 계정에 접근하지 않는다.
   - **(d) 배정표가 정본**: 최종 계정↔페르소나↔웨이브 배정은 **`qa-lead`가 배포하는 배정표**를 따른다. 배정표가 없으면 **착수하지 않는다**(상태 오염 방지).
5. 각 태스크 시작 전 **정지선 필드를 먼저 읽는다**. 이 묶음에서 정지선을 넘으면 되돌릴 수 없다.
6. **URL 파라미터 취득법 — 우회 진입 태스크 착수 전 필독**(검수 지적 B-19).

| 파라미터 | 어디서 얻나 | 못 얻으면 |
|---|---|---|
| `siteId`(T3·T10) | **내 사이트 관리(`/my/sites`)의 사이트 카드**에서 확인한다. 카드 제목("쏠쏠한 도탑 ›")을 클릭했을 때 이동하는 주소, 또는 카드 링크의 주소에 포함된 식별자다. **얻는 방법을 모르면 억지로 찾지 말고 `qa-lead` 배정표에 사전 기재된 값을 쓴다.** | 경로①(정상 클릭)만 수행하고 경로②는 **`[미확인]`(파라미터 취득 불가)**로 기록 |
| `subscriptionId`(T8·T9·T11) | **현재 구독 레코드가 0건이라 실제 값이 존재하지 않는다.** 시나리오가 요구하는 것은 **임의값을 넣었을 때의 에러·empty 분기 관찰**이므로 아무 값(예: `1`)이나 넣는다. | — |
| `reason`(T6) | 임의값. 문구가 바뀌는지 보기 위한 것 | — |

   - **배정 규칙**: **URL 우회 태스크(T3·T5·T6·T8·T9·T10·T11)는 디지털 친숙도 '중·상' 페르소나에 우선 배정**한다. **친숙도 '하' 페르소나는 경로①(정상 클릭)만 수행**하고 경로②는 수행하지 않는다 — **경로① 체감이 이 묶음의 1급 데이터이므로 손실이 없다.**

> 표기 규약
> - **【재현】** = 이미 문서화된 **미해결(open)** blocker·결함을 다시 밟는 태스크. **"막히면 성공"**이다. 신규 이슈로 올리지 말고 기존 ID(RSK-00N / D0N)로 연결한다.
> - **【회귀 스모크】** = **이미 수정·배포 완료된** 항목이 다시 깨지지 않았는지 보는 태스크. **정상 동작이 성공**이며, **【재현】과 판정 방향이 정반대**다. 이 라벨이 붙은 태스크에서 "막혔다"면 그것은 **회귀 결함**이다.
> - **【문서 대조】** = 화면 조작이 아니라 문서와 대조만 하는 태스크(메일 8종).
> - **미완주(정지선 준수)** = 정지선에서 의도적으로 멈춘 결과. **"미검증"이 아니라 "여기까지 하고 멈췄음"**으로 기록한다.
>
> **판정 3값 규약(전 태스크 공통)** — 각 성공 기준은 반드시 셋 중 하나로 닫는다:
> **합격** / **불합격** / **`[미확인]`**(도달 실패·데이터 부재·정지선 준수). **"정상"으로도 "결함"으로도 단정할 수 없는 것은 전부 `[미확인]`**이다.
> 성공/실패를 가르지 않고 사실만 적도록 설계된 항목에는 **`[관측 전용 — 판정 없음]`** 라벨을 붙여, 통합 담당이 **"미수행"과 혼동하지 않게** 한다.
>
> ⚠️ **문서 신뢰 경고(검수 §5-10)**: 이 시나리오가 인용한 storyboard 기대 문구는 **표본 28개만 정밀 대조**된 상태이며, **문서가 결함을 은폐한 사례가 1건 확인**됐다(`_storyboard-qa4-frontend.md:71`, `1201-001` "특이사항 없음"). **문서 문구와 실물이 다르면 실물을 정본으로 기록**한다.

### J3. 가격 탐색 → 유료 전환(신규 결제)

#### T1. 내게 맞는 요금제를 고른다
- **목표**: 요금제 페이지에서 플랜별 가격·혜택·수수료를 비교해 "내가 살 플랜"을 스스로 하나 정한다(구매는 아직 하지 않는다).
- **시작 지점**: 홈 또는 헤더의 가격 메뉴. **비로그인 상태에서 먼저 한 번, 로그인 상태에서 다시 한 번** 본다.
- **성공 기준**:
  1. 플랜 5종(Free·Basic·Growth·Advanced·Enterprise)의 **월 요금·플랫폼 수수료**를 화면에서 읽어 말할 수 있다.
  2. **월간/연간 토글을 바꾸면 가격만 바뀌고**, 수수료·제한값은 그대로임을 확인한다(BR-R-033).
  3. 연간 선택 시 **30% 할인**이 반영된 금액이 보인다(Basic 100,000 → 70,000, BR-R-032).
  4. Enterprise는 숫자가 아니라 **"협의"**로 표기된다(다른 플랜의 빈 값="무제한"과 구분, BR-R-034).
  5. 하단 **요금제 비교 아코디언**의 그룹을 펼쳐 항목을 볼 수 있다.
  6. 페르소나가 **"나는 어떤 플랜을 살지"를 한 문장으로 말할 수 있다**(못 정하겠다면 그 이유가 결과다).
- **관찰 포인트**:
  - **플랜 카드의 수치와 하단 비교표의 수치가 서로 다른 곳**이 있는가(학습자 수·저장 용량·강의 수·관리자 계정·수수료 정의). 있다면 그 항목을 그대로 인용한다. → **BR-R-035는 `[미확정]`이라 "어느 쪽이 맞다"고 판정하지 말고 "불일치가 있다"까지만 적는다.**
  - `GET /api/plans`가 느리거나 실패했을 때 **로딩/에러(재시도)/빈 목록** 중 무엇이 보이는가.
  - 요금제가 **"이 돈을 낼 만하다"고 설득하는가** — 특히 Free(수수료 10%)와 Basic(수수료 0%, 월 10만원)의 손익 분기를 페르소나가 스스로 계산해낼 수 있는가.
  - `/pricing`이 홈 가격표 스텁(`0601-006`)과 **같은 화면으로 수렴**하는가(별도 가격표 화면이 따로 존재하는가).
  - 모바일에서 5개 플랜 카드가 가로 스크롤인지 세로 스택인지, 비교표가 읽히는지.
- **커버 화면ID**: `S-BR01-0601-001`, `S-BR01-0601-006`
- **관련 규칙**: BR-R-031·032·033·034·035
- **정지선**: 해당 없음(열람만).

#### T2. 【재현】 마음에 든 유료 플랜을 사려고 시도한다 — 정상 클릭 경로
- **목표**: 요금제 페이지에서 **버튼만 눌러서** 결제 화면까지 가본다. 주소창을 직접 건드리지 않는다.
- **시작 지점**: 가격 페이지(T1의 연장). **로그인한 상태**에서 시작한다.
- **성공 기준** — ★ 이 태스크는 **"결제 화면에 도달하지 못하는 것"이 성공이다**:
  1. 유료 플랜(Basic/Growth/Advanced)의 **"구매하기"를 눌렀을 때 최종 착지 URL을 기록**한다. 기대 관측: `/login?next=/my/sites`를 경유해 **`/my/sites`(내 사이트 관리)에 착지** — 결제 화면이 아니다.
  2. 3개 유료 플랜 CTA **전부**가 같은 곳으로 가는지 확인한다.
  3. `/my/sites`에 도착한 뒤, 거기서 **다시 유료로 올라가는 길을 찾아본다**(사이트 카드의 "플랜 업그레이드" 등). → 비활성이라 길이 끊긴다.
  4. 위 1~3이 관측되면 **RSK-002 재현 성공**으로 기록한다. **"테스터가 길을 못 찾았다"가 아니라 "앱에 길이 없다"**이다.
  5. **Free 플랜 "무료로 시작하기"를 로그인 상태에서** 눌러본다. 회원가입 폼(`/signup`)으로 가면 **RSK-014 재현 성공**(이미 로그인했는데 다시 가입하라고 한다).
- **관찰 포인트**:
  - 페르소나가 **"구매하기를 눌렀는데 왜 여기 왔지?"**를 자각하는가, 아니면 자기가 뭘 잘못했다고 생각하는가. **후자라면 그 심리를 그대로 인용해 적는다**(이 blocker의 실제 사용자 피해가 그것이다).
  - 결제 화면으로 가려고 **몇 번 시도했고 몇 분을 썼는가**. 포기 시점을 기록한다.
  - 헤더 "주요 기능"·"고객센터"가 눌러도 반응 없는 **죽은 메뉴**인데, 길을 잃은 사용자가 이걸 눌러 도움을 찾으려다 또 막히는가(실물지도 §5-5).
  - 로그인 상태인데 헤더에 **"무료로 시작하기"**가 계속 보이는 것이 혼동을 더하는가(실물지도 §5-7).
- **커버 화면ID**: `S-BR01-0601-001`(CTA 배선)
- **관련 규칙**: BR-R-031 / RSK-002(open blocker) · RSK-014
- **정지선**: **#1 적용(방어적)** — "도달하지 못할 것"을 전제하지 않는다. **만약 어떤 경로로든 결제 화면에 도달했다면 즉시 정지선 #1이 발동**해 [결제하기] 활성화 확인까지만 하고 클릭하지 않는다. **개발자도구로 링크를 고쳐 진입하지 않는다.**

#### T3. 【재현】 결제 화면에서 결제 직전까지 진행한다 — 우회 진입
- **목표**: (T2에서 정상 경로가 끊긴 것을 확인한 뒤) 결제 화면 **내부**가 제대로 만들어져 있는지 확인한다. 결제는 **하지 않는다**.
- **시작 지점**: ★ **T2(경로① 정상 클릭)를 먼저 끝낸 뒤에만 착수한다**(리드 판정 B-3 순서 강제 — 전제 1 참조). 그다음 주소창에 `/purchase?siteId=<내 사이트 ID>` 직접 입력(사이트를 가진 계정 필요, 파라미터 취득법은 §3 사전조건 6). **먼저 파라미터 없이 `/purchase`로 진입해 본다.**
- **성공 기준**:
  1. **파라미터 없이 진입** 시 "대상 사이트를 확인할 수 없어요" + "내 사이트 관리하기에서 플랜을 구매할 사이트를 먼저 선택해 주세요" + 이동 버튼이 보인다(empty 분기 정상).
  2. `siteId`를 붙여 진입하면 좌측 **선택된 플랜 요약**(플랜·주기·대상 사이트·구독 기간(예상)·결제 예정 금액)과 우측 **결제하기 카드**가 보인다.
  3. **플랜 탭을 전부 눌러본다** — 어떤 탭을 눌러도 **화면이 하얗게 죽거나 가격이 `NaN`/빈칸/`0원`으로 나오지 않는다**. **Enterprise 탭이 목록에 노출되면 그 자체가 미수정 신호**다.
     - ★ **회귀 스모크 성격**: **RSK-006은 2026-07-28 수정·배포 완료**(`BR01-r05.md` — 커밋 확인)이고 **실사이트 실측에서 Basic/Growth/Advanced 3종만 확인**됐다(`03_실사이트-실물지도.md:70`, 2026-07-28). 즉 **정상 동작이 기대값**이며 여기서 이상이 나오면 **회귀 결함**이다. "찌를 곳"이 아니라 **회귀감시 항목**으로 다룬다(02b §5-1).
  4. 월간/연간 토글을 바꾸면 **결제 예정 금액이 따라 바뀐다**(VAT 포함 표기).
  5. **카드 미선택 상태로 결제를 시도**하면 "결제 정보 등록은 필수입니다"가 뜬다(BR-R-036).
  6. **약관 미동의 상태로 결제를 시도**하면 "약관 동의는 필수입니다"가 뜬다(BR-R-036).
  7. 카드 선택 + 약관 동의를 모두 채우면 **[결제하기]가 활성화된다** — ★ **여기까지 확인하고 멈춘다. 클릭하지 않는다.** 결과는 **"미완주(정지선 준수)"**로 기록한다.
- **관찰 포인트**:
  - ★ **약관 문구 정합성**: 이 화면은 **Basic ₩100,000(유료)** 결제 화면인데, 동의 체크박스가 **"쏠쏠 무료약정상품 구매 약관에 동의합니다"**를 가리킨다(실물지도 §5-3). 푸터에는 **"유료약정상품 이용약관"이 따로 존재**한다. → **페르소나가 이 불일치를 알아채는가? 알아챘다면 어떤 기분인가(돈 내는 화면인데 무료 약관에 동의하라고 한다)**를 그대로 적는다. 약관 링크를 눌러 어떤 문서가 열리는지도 확인한다.
  - **"결제 정보 등록은 필수입니다"가 두 줄 연속 중복 출력**되는가(실물지도 §5-4).
  - "구독 기간(예상)"에 붙은 **`결제 전 예상치` 배지**가 사용자에게 어떻게 읽히는가(안심? 불신?) — 전제 3.
  - **"구독서비스 결제 안내"** 블록이 이 화면에 있는가(T8·T10과 대조하기 위한 기준점 — RSK-018).
  - 결제 직전에 **총 얼마가 언제 빠져나가는지**를 페르소나가 확신할 수 있는가.
  - 모바일에서 좌우 2열이 어떻게 접히고, [결제하기]가 화면 밖으로 밀리지 않는가.
- **커버 화면ID**: `S-BR01-0601-002`
- **관련 규칙**: BR-R-036·050·051 / RSK-006 · RSK-018
- **정지선**: **#1 실결제 최종 승인 금지** — "카드 선택 + 약관 동의까지 진행해 **[결제하기] 버튼이 활성화되는 것까지만 확인**하고 클릭하지 않는다. 비활성 조건(카드 미선택·약관 미동의) 검증은 자유롭게 수행한다."

#### T4. 결제에 쓸 카드를 등록한다
- **목표**: 결제수단이 없다는 것을 확인하고, 카드를 등록해 결제 준비를 마친다.
- **시작 지점**: 계정 관리 화면의 결제 수단 영역(**"+ 카드 등록하기"**) — 이 경로는 **정상 클릭 경로로 살아 있다**. 결제 화면의 "+ 카드 등록하기"로도 진입해 본다.
- **성공 기준**:
  1. 카드가 없을 때 **"등록된 결제 수단이 없습니다"**(계정관리) / **"등록된 카드가 없습니다"**(결제 화면) 빈 상태가 보인다.
  2. 등록 화면에서 **카드사(9종)·카드 종류(신용/체크)·카드번호 뒤 4자리·대표 카드 설정** 항목을 입력할 수 있다.
  3. **뒤 4자리에 숫자가 아닌 값·3자리·5자리를 넣으면** "카드 번호 뒤 4자리(숫자)를 입력해 주세요" 오류가 뜬다(BR-R-049).
  4. 정상 입력 후 등록하면 **"카드가 등록되었습니다"**와 함께 **"실 카드 인증(토스페이먼츠)은 스테이징 게이트로 비활성화되어 있습니다"** 안내 모달이 뜬다(무음 성공 위장을 하지 않는다).
  5. 모달을 닫으면 **원래 있던 화면(`next` 목적지, 기본 `/my/account`)으로 돌아오고**, 결제 수단 목록에 방금 등록한 카드가 마스킹(`**** **** **** 1234`)되어 보인다(BR-R-051).

> | # | 조건 |
> |---|---|
> | **C-1 (핵심·순서 강제)** | 🔴 **`_pu03`(카드 1장 상태의 최소1장 유지 안내) 검증 = T16을 반드시 먼저 끝낸 뒤에** 2번째 카드를 등록한다. **역순 불가.** |

> **실행 순서(지정 계정 전담 페르소나만)**

> ② T16 전체         — 카드 1장 상태에서 [삭제] → _pu03 관찰  ← 여기를 반드시 통과

- **정지선**: **#6 카드 등록** — "폼 입력·뒤4자리 검증 오류까지. 제출은 staging-gate지만 `POST /api/billing/cards`가 호출되므로 **테스트 계정 1회로 한정**하고, 이후 삭제 시도는 #4 정지선을 따른다."

#### T5. 결제가 끝났다면 무엇을 보게 되는지 확인한다
- **목표**: 결제 성공 화면이 사용자에게 **무엇을 확인시켜 주는지**를 본다.
- **시작 지점**: 정상 경로는 T3의 [결제하기] 성공 — **정지선 #1로 금지된다.** 따라서 `/purchase-complete`로 직접 진입해 화면 존재만 확인한다.
- **성공 기준**:
  1. `/purchase-complete`(파라미터 없음)로 진입했을 때의 거동을 기록한다 — 화면이 뜨는가, 오류가 나는가, 빈 값으로 뜨는가.
  2. 화면이 뜬다면 **결제 정보(플랜·금액·다음 결제일·카드 마스킹)** 자리와 **[쏠쏠 바로가기]** 버튼이 있는지 확인한다.
  3. **정상적인 결제 성공 데이터로 이 화면을 보는 것은 도달 불가**임을 명시하고 **`[미확인]`**으로 남긴다(정지선 #1 + 유료 결제 계정 부재).
- **관찰 포인트**:
  - 이 화면이 **"결제 완료"라고 단정하는가**, 아니면 상태(`subState=pending`)에 따라 문구를 나누는가(BR-R-050 — 무음 성공 위장 금지).
  - ⚠️ **판정 주의(오탐 방지)**: **파라미터 없는 `/purchase-complete` 직접 진입은 사용자가 실제로는 밟지 않는 비정상 경로**다. 여기서 정적 완료 문구가 보이더라도 **결함으로 단정하지 않는다** — 파라미터 필수 여부가 설계상 어떻게 정해졌는지는 `[미확인]`이다. **문구를 그대로 인용해 기록하고 "설계 확인 대상"으로 올린다.** `[관측 전용 — 판정 없음]`
  - 결제 후 "그래서 이제 뭘 하면 되나"가 안내되는가.
- **커버 화면ID**: `S-BR01-0601-003`
- **관련 규칙**: BR-R-050·051
- **정지선**: **#1** — 결제를 실행해 이 화면에 도달하려 시도하지 않는다.

#### T6. 결제가 실패했다면 무엇을 보게 되는지 확인한다
- **목표**: 결제 실패 화면이 **원인과 다음 행동**을 알려주는지 확인한다.
- **시작 지점**: `/purchase-failed` 및 `/purchase-failed?reason=<임의값>` 직접 진입.
- **성공 기준**:
  1. 실패 안내 문구와 **[가격 페이지로 이동하기]**(또는 동등한 복구 버튼)가 보인다.
  2. `reason` 값에 따라 문구가 바뀌는지, 아니면 고정 문구인지 기록한다.
  3. **`reason` 없이 진입했을 때 빈 문구·`undefined` 등 깨진 표기가 나오지 않는다.**
- **관찰 포인트**:
  - 페르소나가 **"내 돈이 빠져나갔나 안 빠져나갔나"**를 이 화면만 보고 확신할 수 있는가. 확신 못 한다면 그것이 가장 중요한 발견이다.
  - 카드 한도초과·승인거부 같은 **구체적 원인**이 나오는가, 뭉뚱그린 안내인가.
  - 재시도 경로가 제시되는가(가격 페이지로 돌아가라는 안내는 "다시 결제하라"는 뜻으로 읽히는가).
- **커버 화면ID**: `S-BR01-0601-005`
- **관련 규칙**: BR-R-042(재시도 3일/6회 → 유예 27일 정책과의 연결) / 화면 문구는 storyboard 미보유 → **기대 문구를 단정하지 말 것**
- **정지선**: 해당 없음.

### J4. 플랜 업그레이드 / 결제주기 변경(월↔연)

#### T7. 【재현】 지금 쓰는 사이트의 플랜을 올린다 — 정상 클릭 경로
- **목표**: 내 사이트 관리 화면에서 **"플랜 업그레이드"**를 눌러 상위 플랜으로 올리려 한다.
- **시작 지점**: 내 사이트 관리(사이트를 가진 검수 계정으로 로그인).
- **성공 기준** — ★ **버튼이 안 눌리는 것이 성공(재현)이다**:
  1. 사이트 카드에서 **"플랜 업그레이드"·"구독 취소하기" 버튼이 회색 비활성**임을 확인한다.
  2. 버튼에 마우스를 올렸을 때 **"구독 정보를 불러오지 못했어요"** 툴팁이 뜨는지 확인한다.
  3. 클릭해도 아무 일이 일어나지 않음을 확인한다.
  4. 위가 관측되면 **실물지도 §5-1 재현 성공**으로 기록한다.
  5. ★ **문구 정합성 지적**: 실제로는 `GET /api/subscriptions`가 **정상 응답(200)으로 "구독 없음"**을 반환하는 상태다. 즉 **"불러오지 못했어요"(오류)와 "구독이 없어요"(정상 상태)가 서로 다른 말인데 같은 문구로 처리**되고 있다. 페르소나가 이 문구를 읽고 **"서비스가 고장 났다"고 오해하는지**를 기록한다.
- **관찰 포인트**:
  - 무료 플랜 사용자가 **유료로 올라갈 방법을 이 화면에서 찾을 수 있는가**(T2와 합쳐 "이 서비스에서 돈을 낼 방법이 없다"는 결론에 도달하는가).
  - **RSK-015 확인 포인트는 2개로 좁힌다**(02b §5-6 정정) — ★ **먼저 알아야 할 사실: "다음 결제일" 라벨은 값이 `-`인 채로 실물에 존재한다**(`03_실사이트-실물지도.md:62` 실측, "다음 결제일 -"·"플랜 무료" 공존). 따라서 **"다음 결제일이 보이니 해소됐다"고 판정하면 오판정**이다. 실제로 없는 것은 아래 둘뿐이다:
    - **① 경고 배너 부재**(영상용량 90% 초과·만료 임박 등) **② 잔여일 표기 부재**. 이 둘의 부재만 RSK-015 재현으로 기록한다.
  - **`사용량 미연동` 배지**(영상용량 0GB / 회원 0명)가 사용자에게 어떻게 읽히는가 — 전제 3. ★ **회귀 스모크 성격**: RSK-007(사이트 카드 용량 표기)은 **2026-07-28 수정·배포 완료**이고 실측에서 "0GB" 정상 표기가 확인됐다 → **정상이 기대값**이며 "찌를 곳"이 아니다(02b §5-1).
  - 상태 배지 **"개설 중"**이 언제 끝나는지 사용자가 알 수 있는가.
- **커버 화면ID**: `S-BR01-0601-004`(진입 경로 측면)
- **관련 규칙**: BR-R-030·038 / 실물지도 §5-1 · RSK-015 · RSK-020
- **정지선**: 해당 없음(버튼이 비활성이라 진행 자체가 불가).

- **관찰 포인트**:

### J5. 결제 실패 복구 · 만료 연장

#### T9. 곧 만료되는 구독을 연장한다
- **목표**: 구독을 1·6·12개월 연장하려 할 때 **얼마가 청구되는지**를 확인한다.
- **시작 지점**: 정상 경로는 사이트 카드의 연장 버튼(만료임박/만료 상태에서만 노출 — 현재 계정엔 해당 상태 없음). 따라서 `/my/product-auto-renew` 및 `?subscriptionId=<임의값>` 직접 진입.
- **성공 기준**:
  1. 구독이 없을 때 **"구독 없음" empty 안내**와 "내 사이트 관리하기" 유도가 보인다(로딩→에러→empty 3분기 중 무엇으로 끝나는지 기록).
  2. 화면이 렌더된다면: **연장 개월 1/6/12 토글**이 있고, 하나를 반드시 골라야 결제로 진행된다(BR-R-041).
  3. 개월을 바꾸면 **결제 예정 금액이 따라 바뀌고**, **`견적(확정 아님)` MockBadge**가 붙어 있다.
  4. 카드 미선택·약관 미동의 시 결제 버튼이 비활성이다(BR-R-036).
  5. **실 구독 데이터 부재로 연장 견적 본체에 도달하지 못하면 `[미확인]`**으로 남긴다.
- **관찰 포인트**:
  - **6개월 10% / 12개월 30% 할인**이 화면에 명시되는가. 명시된다면 그것이 **`[추정]` 값**임을 배지로 고지하는지 확인한다(BR-R-041 — 서버 TODO 기반 추정치).
  - "연장하면 콘텐츠·학습자 데이터가 유지된다"는 안심 안내가 있는가.
  - 만료 임박 사용자가 **이 화면에 스스로 도달할 방법이 있는가**(현재 사이트 카드에서 진입 버튼을 볼 수 없다면 그 사실을 기록).
  - 현재 플랜 등급 배지 누락(RSK-033).
- **커버 화면ID**: `S-BR01-0801-001`
- **관련 규칙**: BR-R-036·041 / RSK-033
- **정지선**: **#1** — [결제하기] 활성화 확인까지. 클릭 금지 → **"미완주(정지선 준수)"**.

#### T10. 결제가 밀린 요금을 지금 낸다(즉시 결제)
- **목표**: 결제 실패·유예 상태에서 **미납 금액을 즉시 결제해 서비스를 정상화**하려 한다.
- **시작 지점**: `/my/product-pay-now` 및 `?siteId=<내 사이트 ID>` 직접 진입.
- **성공 기준**:
  1. 재시도할 청구서가 없을 때 **"이미 정상 처리되었거나 재시도 대상이 아닌 상태입니다"** empty 안내가 정확히 보인다. → **이것이 이 태스크의 주된 확인 대상**이다(정상 empty).
  2. 화면이 렌더된다면: **청구 기간·결제 마감일·재시도 횟수**와 **결제 금액 요약(청구 금액·VAT·미납 이월 금액·산정된 결제 금액)**이 보인다.
  3. **미납 이월 금액은 0보다 클 때만 행이 노출**된다.
  4. 카드 미선택·약관 미동의 시 결제 버튼 비활성(BR-R-036).
  5. **미납 청구서 데이터가 없어 금액 요약 본체에 도달 불가 → `[미확인]`**.
- **관찰 포인트**:
  - **"재시도 대상이 아닌 상태"**라는 말을 페르소나가 이해하는가. "내 결제가 밀린 건가 아닌가"를 이 문구로 판단할 수 있는가.
  - **자동결제 실패 후 흐름**(재시도 3일/6회 → 유예 27일 → 해지, BR-R-042)이 화면 어디에도 설명되지 않는가. 사용자가 "언제까지 내야 서비스가 안 끊기나"를 알 수 있는가.
  - **"구독서비스 결제 안내" 블록 누락**(T3 `/purchase`와 비대칭 — RSK-018) 및 플랜 등급 배지 누락(RSK-033).
- **커버 화면ID**: `S-BR01-0801-002`
- **관련 규칙**: BR-R-036·042·043 / RSK-018 · RSK-033
- **정지선**: **#1** — [결제하기] 활성화 확인까지. 클릭 금지 → **"미완주(정지선 준수)"**.

### J6. 구독 취소

#### T11. 구독을 그만둔다 — 정상 경로 + 우회 진입
- **목표**: 더 이상 쓰지 않기로 하고 구독을 취소하려 한다. **취소를 확정하지는 않는다.**
- **시작 지점**: ① 사이트 카드의 **"구독 취소하기"**(현재 `is-disabled` — T7과 동일 재현) → ② `/my/product-cancel` 및 `?subscriptionId=<임의값>` 직접 진입.
- **성공 기준**:
  1. **경로 ①**: "구독 취소하기" 버튼이 비활성이라 정상 경로로 취소를 시작할 수 없음을 확인·기록한다(재현).
  2. **경로 ②**: 구독이 없을 때 **"이미 해지된 구독이에요"** 또는 구독 없음 empty 중 무엇이 나오는지 정확히 기록한다(BR-R-046).
  3. 화면이 렌더된다면: **"구독 취소가 아쉬워요!"** 안내와 함께 ①기간 종료일까지 계속 이용 가능 ②자동 갱신 비활성화 ③카드 정보 자동 삭제 ④재가입 언제든 가능 4개 안내와 **현재 플랜·구독 만료 예정일**이 보인다.
  4. **이미 취소 예약된 구독**이면 취소 버튼이 **숨겨지고** "이미 구독 취소가 예약되어 있어요 — {만료일}까지 계속 이용하실 수 있어요"만 노출된다(BR-R-046).
  5. ★ [구독 취소하기]를 누를 수 있는 상태라면 **누른다 → 확인 모달 "정말 구독을 취소하시겠어요?"가 뜬 것까지 확인하고, [취소]로 닫는다.** 결과는 **"미완주(정지선 준수)"**.
  6. 구독 데이터 부재로 3~5에 도달하지 못하면 **`[미확인]`**.
- **관찰 포인트**:
  - ★ **정지선 경고 재확인**: 이 화면의 확정 버튼은 **실 API(`DELETE /api/subscriptions/:id`)를 실제로 호출**한다(오너 승인 accepted-risk). **모달의 [확인]을 누르면 진짜로 취소된다.** 페르소나는 **절대 누르지 않는다.**
  - 취소 안내가 **"환불"에 대해 무엇을 말하는가**. "기간 만료까지 이용 가능"과 "환불 없음"이 구분돼 읽히는가, 아니면 **환불이 될 것처럼 읽히는가**(RSK-027 — 이 오해가 CS 1순위 위험).
  - **"카드 정보 자동 삭제"** 안내가 불안을 주는가(다른 결제에 쓰는 카드도 지워지나?).
  - 취소를 망설이게 하는 장치(만류)가 과한가 적절한가.
- **커버 화면ID**: `S-BR01-0801-003`
- **관련 규칙**: BR-R-045·046 / RSK-027
- **정지선**: **#2 구독 취소 확정 금지** — "`/my/product-cancel` 진입 → 안내·현재 구독 정보 확인 → [구독 취소하기] 클릭 → **확인 모달('정말 구독을 취소하시겠어요?')이 뜬 것까지**. 모달의 [확인]은 누르지 않고 [취소]로 닫는다." **← 이 정지선을 넘으면 검수 계정의 구독이 실제로 취소된다.**

#### T12. 구독 취소가 끝났을 때 무엇을 안내받는지 확인한다
- **목표**: 취소 완료 안내가 **"언제까지 쓸 수 있는지"와 "환불은 어떻게 되는지"**를 알려주는지 확인한다.
- **시작 지점**: T11의 확인 모달에서 [확인]을 눌렀을 때 — ★ **정지선 #2로 금지**. 따라서 **이 모달은 실사용 검증 대상이 아니다.**
- **성공 기준**:
  1. 이 모달에 도달하려면 실제 구독 취소가 필요하므로 **도달하지 않는다**. 결과를 **`[미확인]`(정지선 #2 준수 — 의도적 미도달)**로 기록한다. **"검증 실패"가 아니다.**
  2. 대신 **문서 기준으로 기대 문구를 확인만 하고 기록**한다: "구독 취소가 완료되었습니다" + "내 사이트 관리하기에서 확인하실 수 있습니다" + [확인] 버튼 1개.
  3. **문서 대조 지적 1건**: 이 완료 문구에 **이용 가능 종료일도, "환불 없음"도 없다**. → "완료"라는 긍정 톤이 **"환불도 처리됐다"는 오해**를 부를 수 있다는 관점을 리포트에 남긴다(RSK-027).
- **관찰 포인트**:
  - 취소 성공 후 사용자가 **"내 사이트는 지금 당장 멈추나?"**를 알 수 있는가(만료까지 유지가 정상 동작).
  - 취소 완료 시점에 **구독 취소 안내 메일(`1201-010`)이 함께 트리거**되는데, 모달 문구와 메일 문구가 **서로 다른 말을 하지 않는지** 대조한다(T27과 연계).
- **커버 화면ID**: `S-BR01-0801-003_pu01`
  - **레거시 참조 확인(1줄)**: `S-BR01-0801-001_pu01`은 구 넘버링에서 유래한 **죽은 참조**(대응 파일 없음, 현재 `0801-001`은 "자동연장하기"로 재배정)이며 `0801-003_pu01`과 **동일 콘텐츠**다 — **중복 테스트하지 않는다.** 리포트에는 "레거시 참조로만 확인, 별도 검증 없음"으로 1줄 기재한다.
- **관련 규칙**: BR-R-045 / RSK-027
- **정지선**: **#2** — 이 모달을 띄우기 위해 취소를 확정하지 않는다.

### J7. 결제수단(카드) 관리 · 계정

#### T13. 내 계정 정보를 확인하고 고친다
- **목표**: 이름·비밀번호·수신 설정·결제수단·결제 이메일을 한 화면에서 확인하고 필요한 것을 바꾼다.
- **시작 지점**: 헤더의 내 계정 메뉴 → 계정관리.
- **성공 기준**:
  1. **아이디(이메일)가 수정 불가(readonly)**이고, 바꿀 수 없다는 안내가 있다(BR-R-012).
  2. **비밀번호 변경은 현재 비밀번호 확인을 요구**한다. 현재 비밀번호를 비운 채 저장하면 "비밀번호를 입력해 주세요" 계열 오류로 막힌다(BR-R-013).
  3. 새 비밀번호와 확인이 다르면 불일치 오류가 뜬다.
  4. **마케팅 정보 수신 토글**이 있고, 상태를 바꿔 저장할 수 있다. **(2단계 인증 토글은 이 기준에서 제외 — 아래 별항 참조)**
  5. **결제 수단 영역**에 카드 목록(또는 "등록된 결제 수단이 없습니다" 빈 상태)과 **"+ 카드 등록하기"**가 있다.
  6. **결제 이메일 영역**에 현재 이메일과 **[이메일 변경]** 진입이 있다.
  7. 저장 후 화면을 새로고침해도 **마케팅 수신 등 저장 대상 값**이 유지된다. **(2단계 인증은 제외 — 아래 별항)**
  8. ★ **별항 — 2단계 인증 토글은 성공/실패 판정 대상이 아니다**: 이 토글에는 **`저장 미구현` 배지**가 붙어 있고 **실제로 저장되지 않는 것이 의도된 상태**다. 따라서 **저장 미반영 자체를 결함으로 올리지 않는다**(올리면 오탐). **검증 대상은 단 하나 — "사용자가 저장됐다고 착각하는가"**이며, 착각한다면 그것을 **신뢰·보안 관점의 UX 이슈**로 기록한다. `[관측 전용 — 판정 없음]`
- **관찰 포인트**:
  - **2단계 인증 옆의 `저장 미구현` 배지** — 토글을 켜고 저장했는데 실제로는 저장되지 않는다. 페르소나가 **"보안 설정을 켰다"고 착각하는가**? 착각한다면 그것은 **신뢰·보안 관점의 중대한 UX 문제**다(배지는 의도된 표식이지만, 그 표식이 사용자에게 통하는지는 별개).
  - **결제 이메일 옆의 `EP 미비` 배지**도 같은 관점으로 관찰한다.
  - 마케팅 수신을 꺼도 **중요 공지는 계속 온다**는 안내가 있는가(BR-R-015).
  - 폼 오류 시 **필드 옆 빨간 아이콘이 없는가**(RSK-012/D09 — 이 화면도 8개 영향 폼 중 하나).
  - **[계정삭제]가 눈에 잘 띄는 위치에 있는가**(실수로 누를 위험 vs 못 찾을 위험).
  - 한 화면에 계정·보안·결제수단·결제이메일·탈퇴가 다 몰려 있는 구조가 **찾기 쉬운가 부담스러운가**(구조적 관점).
- **커버 화면ID**: `S-BR01-0901-001`
- **관련 규칙**: BR-R-012·013·014·015·051 / RSK-012
- **정지선**: **#3**(계정삭제는 T18에서만) · **#4**(카드 조작은 T14~T17에서만). 이 태스크에서는 **[계정삭제]를 누르지 않는다.**

#### T14. 다른 카드를 대표 카드로 바꾼다
- **목표**: 결제에 기본으로 쓸 카드를 다른 카드로 바꾼다.
- **시작 지점**: 계정관리 → 결제 수단 목록에서 **대표가 아닌 카드의 [대표 카드 설정] 버튼 클릭**.
- **성공 기준**:
  1. **이미 대표인 카드에는 [대표 카드 설정] 버튼이 아예 없고** '대표 카드' 배지만 보인다.
  2. 대표가 아닌 카드의 [대표 카드 설정]을 누르면 확인 모달이 뜨고, 문구가 **`{카드사}(****{끝4자리}) 카드를 대표카드로 등록 하시겠습니까?`** 형식이다(BR-R-055).
  3. 모달에 [취소]/[확인] 두 버튼이 있다.
  4. ★ **[확인]을 누르지 않고 [취소]로 닫는다** → **"미완주(정지선 준수)"**.
  5. **전제 — 카드 2장 필요**: 이 모달을 띄우려면 **카드가 2장 이상** 필요하다.
     - ✅ **지정 계정(B-4 완화 대상)**: T4의 실행 순서 ①→②→③를 마친 상태라면 **도달 가능**하다. **반드시 T16(`_pu03`)을 먼저 끝낸 뒤**여야 한다(C-1).
     - **그 외 계정**: 정지선 #6 원문(1회 등록)이 유지되므로 **도달 불가 → `[미확인]`(데이터 부재)**로 기록한다. **"1회" 제한을 임의로 늘리지 않는다.**
- **관찰 포인트**:

     - 따라서 **"비밀번호 입력란이 있다"를 합격선으로 쓰지 않는다.** 실제로 보이는 요소를 열거해 기록하고, **비밀번호 필드가 없다면 그 자체가 신규 결함 후보**(비가역 액션의 2중 게이트 소실)로 올린다.
     - **정본 관계**: 이 모달의 접근성·구성 기술은 **`05_시나리오-접근성.md` G3-①을 정본**으로 하며, 본 태스크와 결과가 갈리면 **05를 따른다**.
  3. ★ **아무것도 채우지 않고 [탈퇴하기]를 누르면 막힌다** — 동의 미체크 시 "위 내용에 동의해 주세요" 계열 경고가 뜨고 **모달이 유지된다**(BR-R-016).
  4. ★ **(성공기준 2에서 비밀번호 필드가 실제로 존재하는 것이 확인된 경우에만 수행)** 동의만 체크하고 비밀번호를 비운 채 [탈퇴하기]를 누르면 막힌다 — "현재 비밀번호를 입력해 주세요" 계열 경고 + 비밀번호 필드로 포커스가 이동하고 **모달이 유지된다**(BR-R-016). **필드가 없으면 이 기준은 `[미확인]`(해당 없음 — 필드 부재)**로 기록하고, 그 부재 사실을 성공기준 2의 결함 후보에 연결한다.
  5. ★ **차단 조건을 모두 만족시킨 뒤에는 [탈퇴하기]를 누르지 않는다.** [취소]로 닫는다 → **"미완주(정지선 준수)"**.
  6. 모달을 닫은 뒤 계정이 그대로 살아 있음을 확인한다(재로그인 불필요).
- **관찰 포인트**:
  - **게이트가 충분히 신중한가, 과한가**. 페르소나가 "실수로 탈퇴할 위험"을 느끼는가. — ★ **"2중 게이트(동의+비밀번호)"를 전제하지 말고, 성공기준 2에서 실제로 관측한 게이트 구성**을 기준으로 평가한다. **동의 체크 1종뿐이라면 "영구 삭제·복구 불가"를 경고하는 화면치고 게이트가 얇지 않은가**를 묻는다.
  - **원장 게이트 누수 참고**: 탈퇴 관련 **심각도 '상'·상태 open 결함(`br01-r02-D13`)이 `_ledger.md`에 미등재**된 상태다(02b §6-F). 즉 **이 태스크의 관측 결과는 원장 보정 근거로도 쓰인다** — 관측을 상세히 남길 가치가 그만큼 크다.
  - **"영구적으로 삭제되며 복구할 수 없습니다"**라고 단정하는데, 사용자가 **구독·결제가 어떻게 되는지**(남은 기간·환불·자동결제)를 알 수 있는가. **주의사항에 "탈퇴 후 환불·백업 불가"가 명시되는가.**

  - **모달 키보드 접근성**: 이 모달은 카드 모달과 **다른 컴포넌트**라 별도 확인이 필요하다 — Tab 포커스가 모달 밖으로 새는가, Esc로 닫히는가, 닫은 뒤 [계정삭제] 링크로 포커스가 돌아오는가(RSK-011). **비가역 액션이라 포커스 유실 위험이 특히 크다.**

### J8. 결제 이메일 변경

#### T19. 【회귀 스모크】 결제 영수증을 받을 이메일을 바꾼다
- **목표**: 결제 안내를 받을 이메일 주소를 다른 주소로 바꾼다.
- **시작 지점**: 계정관리 → 결제 이메일의 **[이메일 변경]** 클릭. **추가로 `/my/account/billing-email`을 주소창에 직접 입력해서도 진입해 본다.**
- **성공 기준**:
  1. ★ **라우팅 회귀 스모크**: `/my/account`와 `/my/account/billing-email`이 **서로 다른 화면**으로 뜬다(전자=계정 관리, 후자=결제 이메일 변경). 같은 방식으로 `/my/sites`와 `/my/sites/create`도 대조한다.
     - ★ **판정 방향 주의**: **RSK-005는 2026-07-28 수정·배포 완료**이며 **실사이트 실측에서 전용 화면 분리가 확인**됐다(`03_실사이트-실물지도.md:68`). 즉 **정상 분리가 기대값**이고, **후자에 계정 관리 내용이 그대로 나오면 그때가 회귀 결함**이다. 이 태스크는 **【재현】("막히면 성공")이 아니라 【회귀 스모크】("정상이 성공")**이다 — 라벨을 뒤집어 읽으면 판정이 통째로 반대가 된다.
  2. 변경 화면에 **현재 이메일(읽기 전용) / 변경할 이메일 + [인증코드 발송] / 인증코드 + [확인] / 비밀번호** 항목이 보인다.
  3. **이메일 형식이 아닌 값**을 넣고 진행하면 "이메일 주소를 입력해 주세요" 오류로 막힌다.
  4. **인증을 완료하지 않고** 제출하면 "이메일 인증을 완료해 주세요" 오류로 막힌다.
  5. **비밀번호를 비우고** 제출하면 "비밀번호가 맞지 않네요. 다시 입력해 주세요." 오류로 막힌다.
  6. ★ **제출 결과를 관측해 기록한다 — 어느 쪽도 전제하지 않는다.** `[관측 전용 — 판정 없음]`
     - **관측 3갈래**: **(a) 정상 저장**(변경이 실제로 반영됨) / **(b) "결제 이메일 변경 기능은 아직 지원되지 않습니다." 계열 안내로 종료** / **(c) 에러**.
     - **어느 쪽이든 "정상"·"결함"으로 판정하지 말고 사실을 그대로 적는다.**
     - **왜 전제를 세울 수 없나**: 원장 최신본(`BR01-r05.md:98`, 2026-07-28)은 **"billing-email API+화면(`0901-002/003`) 구현 완료"**라 기술하는데, **실물 `/my/account`에는 `EP 미비` 배지가 여전히 노출**된다 → **정면 충돌 `[미확정]`**(02b §5-3). 이전 판(v1.0)의 **"저장되지 않는 것이 정상"** 단정은 이 충돌을 반영하지 못한 stale 서술이었다.
     - **(a)가 관측되면** 그 화면을 **캡처해 보고**한다 — 원장↔실물 충돌을 닫는 1급 증거다.
     - **공통 합격선(어느 분기든 유효)**: **무음 성공으로 위장하지 않는가**. 저장되지 않았는데 성공처럼 보이는 신호를 주면 그것은 결함이다(BR-R-019·BR-R-050).
- **관찰 포인트**:
  - ★ **(b) 분기가 관측된 경우** — **"인증코드까지 다 받고 비밀번호까지 넣었는데 마지막에 '지원되지 않습니다'를 만나는 경험"**을 페르소나가 어떻게 받아들이는가. **화면 진입 시점(또는 [이메일 변경] 버튼 옆)에 미리 알려주지 않는 것**이 시간 낭비·배신감으로 이어지는가 — 이것이 이 태스크의 핵심 관찰이다.
  - **비밀번호가 실제로 맞는지 서버에서 확인하지 않는다**(입력 여부만 검증 — BR-R-020). 아무 값이나 넣어도 통과한다면, **틀린 비밀번호를 넣어보고** 통과하는지 확인해 기록한다(보안 관점 지적, 우회 시도가 아니라 **정상 폼 입력**이다).
  - 폼 오류 시 필드 옆 에러아이콘이 없는가(RSK-012/D09).
  - "다음 결제 이메일부터 적용된다"는 안내가 있는가(BR-R-018 — 다음 결제분부터 적용).
- **커버 화면ID**: `S-BR01-0901-002`
- **관련 규칙**: BR-R-018·019·020 / RSK-005 · RSK-012
- **정지선**: **#9 메일 발송 제한** — "인증/재설정 메일 발송은 **동일 주소 기준 시나리오당 최대 2회**." **[인증코드 발송]을 반복 연타하지 않는다.**

#### T20. 인증코드 발송 안내를 확인한다
- **목표**: 인증코드를 요청했을 때 **얼마 안에 입력해야 하는지** 안내받는다.
- **시작 지점**: 결제 이메일 변경 화면에서 **유효한 이메일 형식을 입력한 뒤 [인증코드 발송] 클릭**(이 조작이 모달을 띄운다).
- **성공 기준**:
  1. 발송 성공 시 안내 모달이 뜨고 **"이메일로 인증코드가 발송되었습니다"** 제목 + **"10분내 인증코드를 등록해 주세요"** 설명이 보인다.
  2. 버튼은 [확인] 하나이며, 닫으면 인증코드 입력으로 이어진다.
  3. 발송 실패 시에는 이 모달이 뜨지 않는다(성공 시에만 노출).
- **관찰 포인트**:
  - **"10분내"가 하드코딩**된 값이다(서버 응답값 미바인딩 — RSK-022/D12). **회원가입 인증코드 모달의 문구와 같은지** 대조하고, 실제로 10분 뒤 코드가 만료되는지는 **시간 소요상 검증하지 않고 `[미확인]`**으로 둔다.
  - 페르소나가 **10분을 충분하다고 느끼는가**(메일함 열고 돌아오는 왕복 시간).
  - 🔴 **코드가 실제로 도착하는가 — "온다/안 온다"를 전제하지 말고 관측해 기록한다.** `[관측 전용 — 판정 없음]`
    - **메일 발송 상태는 `[미확정]`이다**: 구 서술은 "발송 로직 자체가 서버 TODO"였으나, **원장 최신본(`BR01-r05.md:98`, 2026-07-28)은 "메일 발송 스텁+트리거 10건 배선 완료"**를 명시한다 → 충돌(02b §5-3).
    - **안 오면**: "결함"으로도 "미구현이라 정상"으로도 단정하지 말고 **`[미확인]` + 대기 시간·시각을 증거로** 남긴다.
    - **오면**: 본문·링크 정합을 기록한다.
  - 재발송 버튼이 있는가, **연타 제한이 있는가**(RSK-023 — 레이트리밋 부재). 🔴 ★ **실발송 가능성이 생겼으므로 정지선 #9를 엄격 적용한다 — 동일 주소 기준 시나리오당 최대 2회. "어차피 안 나가니까"라는 전제로 연타하지 않는다.** 연타 제한의 존재 여부는 **2회 한도 안에서** 관찰하고, 한도를 넘겨 확인하려 하지 않는다.
- **커버 화면ID**: `S-BR01-0901-002_pu01`
- **관련 규칙**: BR-R-002·004·018 / RSK-022 · RSK-023

#### T21. 결제 이메일 변경이 끝났다는 확인을 받는다
- **목표**: 변경 완료 안내(성공 화면)를 확인한다.
- **시작 지점**: T19의 제출 성공 지점.
- **성공 기준** — ★ **전부 관측형이다. "성공 케이스가 없다"를 전제하지 않는다.** `[관측 전용 — 판정 없음]`
  1. ★ **성공 케이스의 존재 여부 자체가 `[미확정]`이다** — 원장 최신본(`BR01-r05.md:98`, 2026-07-28)은 **`0901-002/003` 구현 완료**라 기술하고, 실물은 **`EP 미비` 배지**를 노출한다(02b §5-3, 정면 충돌). 이전 판(v1.0)의 **"저장 엔드포인트 자체가 없어 성공 화면이 만들어지지 않았다"**는 서술은 이 충돌을 반영하지 못한 stale 단정이므로 **판정 근거로 쓰지 않는다.**
  2. **T19의 제출 결과에 따라 갈라 기록한다**:
     - **T19가 (b)/(c)로 끝났다면** — 완료 화면에 도달하지 못한 것이며 **`[미확인]`(성공 경로 미출현)**으로 기록한다. **"완료 화면이 없다"를 결함으로 단정하지 않는다.**
     - **T19가 (a)정상 저장으로 끝났다면** — ★ **성공 경로가 나타난 것이다. 그 화면을 반드시 캡처해 보고**하고, 완료 안내의 구성(변경된 이메일·적용 시점·다음 행동 안내)을 기록한다. **이것은 원장↔실물 충돌을 닫는 1급 증거**이므로 다른 어떤 관측보다 우선해 남긴다.
  3. **어느 분기든 공통으로 확인할 것 — "완료된 척하지 않는가"**: 저장이 일어나지 않았는데 화면이 **성공처럼 보이는 신호(체크 아이콘·"변경되었습니다"·초록 배너 등)**를 준다면 **그것이 결함**이다(무음 성공 위장 금지, BR-R-019·050).
- **관찰 포인트**:
  - 안내를 닫은 뒤 **입력했던 새 이메일이 화면에 남아 사용자를 헷갈리게 하는가**(바뀐 것처럼 보이는가).
  - **계정관리로 돌아갔을 때 결제 이메일이 어떤 값인가** — 예전 값인지 새 값인지를 **사실대로 기록**한다. **저장 여부가 `[미확정]`이므로 "바뀌면 결함"이라고 판정하지 않는다.** 다만 **"화면 표시와 실제 저장이 어긋나는 경우"**(예: 표시는 바뀌었는데 재로그인하면 원복)는 결함으로 올린다.
  - `EP 미비` 배지가 여전히 노출되는데 실제로는 저장된다면(또는 그 반대라면), **표식과 실제 동작의 불일치** 자체를 이슈로 기록한다.

#### T22. 내가 낸 돈의 내역을 확인한다
- **목표**: 지금까지의 결제 내역을 확인하고 필요하면 영수증을 받는다.
- **시작 지점**: 헤더의 내 계정 메뉴 → 결제내역.
- **성공 기준**:
  1. 결제가 0건인 계정에서 **빈 상태**가 보인다 — "아직 결제 내역이 없네요!" + "텅... 비어있어요..." + "플랜 둘러보러 가기".
  2. 화면이 **백지(콘텐츠 영역 통째로 빈 화면)로 뜨지 않는다** — 안내 문구가 정상 렌더된다. 개발자도구 콘솔에 `TypeError`가 없는지 함께 본다.
     - ★ **회귀 스모크 성격**: **RSK-004는 2026-07-28 수정·배포 완료**이고 **실사이트 실측에서 빈 상태 정상 렌더가 확인**됐다(`03_실사이트-실물지도.md:64`). **정상이 기대값**이며 백지가 나오면 **회귀 결함**이다(02b §5-1 — "죽은 버그에 공수를 넣지 않는다").
  3. 결제 데이터가 있다면: **결제일·플랜·금액·상태 뱃지·[영수증]**이 보이고, **결제완료 행에만 [영수증]**이 노출된다(BR-R-057). → **데이터 0건이라 표 본체·영수증·상태 뱃지는 `[미확인]`(데이터 부재)**.
  4. "플랜 둘러보러 가기"를 누르면 가격 페이지로 이동한다.
- **관찰 포인트**:
  - **빈 상태 문구의 톤**("텅... 비어있어요...")을 페르소나 연령·친숙도별로 어떻게 받아들이는가. 결제라는 **돈 관련 화면에서 이 캐주얼한 톤이 적절한가**(신뢰도 관점) — 이 묶음에서 특히 중요한 관찰이다.
  - 영수증이 **신용카드 매출전표(세금계산서 대체)**임이 안내되는가(BR-R-048). 사업자 사용자가 세금계산서를 찾다 막히는가.
  - 콘솔에 상시 뜨는 `Hydration completed but contains mismatches` 경고가 화면 표시에 영향을 주는가(실물지도 §5-9).
- **커버 화면ID**: `S-BR01-1001-001`
- **관련 규칙**: BR-R-048·051·057·068 / RSK-004
- **정지선**: 해당 없음.

#### T23. 【재현】 결제 내역에서 원하는 건을 찾는다 — 검색·필터
- **목표**: 특정 기간·상태·수단의 결제 건을 걸러낸다.
- **시작 지점**: 결제 내역 화면의 필터바·검색창.
- **성공 기준** — ★ **문서가 정한 규칙을 어기는 것이 관측되면 재현 성공**:
  0. 🔴 **선행 게이트 — 필터 UI가 존재하는지부터 확인한다.** 이 계정은 **결제 0건**이라 목록에 행이 하나도 없다. **빈 상태에서 검색창·필터바가 렌더되는지 여부 자체가 `[미확인]`**이며(02b §7 미해결 5건 중 하나), **행이 0개면 검색·필터의 관찰 대상이 존재하지 않는다**(02b §5-2).
     - **검색창·필터바가 렌더되지 않으면 1~7을 수행하지 않고 `[미확인 — 데이터 부재로 필터 UI 미노출]`로 종료**한다. 이때 **"필터가 없다"를 결함으로 올리지 않는다**(빈 상태에서 감추는 것이 설계일 수 있다).
     - **렌더된다면** 그 사실을 기록하고 1~7로 진행한다. **어느 쪽이든 이 관측 자체가 02b의 `[미확인]` 5건 중 1건을 닫는 값**이므로 캡처를 남긴다.
  1. **검색창에 한 글자만 입력**한다 → 엔터를 치지 않았는데 **목록이 즉시 바뀌면 RSK-001 재현 성공**(오너 확정 전역 규칙 "실시간 필터 금지" 위반). **단 행이 0건이라 "목록이 바뀌는 것"을 눈으로 확인하기 어려우면 `[미확인]`으로 남긴다.**
  2. **돋보기 아이콘을 클릭**한다 → **아무 일도 일어나지 않으면 재현 성공**(핸들러 없음).
  3. **Enter를 눌렀을 때**의 동작을 기록해 1·2와 비교한다.
  4. **× (삭제) 버튼**만 정상 동작하는지 확인한다.
  5. **필터가 몇 개인지 센다** — 기대(문서)는 **기간·결제상태·지급수단 3종 + 초기화 버튼**. 실제로 **지급수단 셀렉트가 없고, 초기화 버튼이 없으면 RSK-016 재현 성공**.
  6. **"기간 전체" 필터를 클릭**한다 → **옵션이 하나도 뜨지 않으면**(readonly 껍데기) 재현 성공.
  7. 조건에 맞는 결과가 0건일 때 **"조건에 맞는 결제 내역이 없어요!"**, 검색 중일 때 **"검색 결과가 없어요!"**로 **문구가 갈리는지** 확인한다(BR-R-068).
- **관찰 포인트**:
  - 검색이 즉시 반응하는 것을 페르소나가 **"편하다"고 느끼는가 "글자 칠 때마다 화면이 튄다"고 느끼는가**. (규칙 위반은 사실이지만, 사용자 체감은 별개 데이터다.)
  - 돋보기를 눌러도 안 되는 것을 **"고장"으로 인지하는가**.
  - 결제 0건 상태에서 필터를 조작할 때 **빈 상태 문구가 조건별로 바뀌는지** 확인 가능한가(데이터가 없어 구분이 어렵다면 `[미확인]`).
- **커버 화면ID**: `S-BR01-1001-001`
- **관련 규칙**: BR-R-057·066·068 / RSK-001(open blocker) · RSK-016
- **정지선**: 해당 없음.

#### T24. 【재현】 마우스 없이 결제 상태 필터를 조작한다 — 키보드 전용
- **목표**: **마우스를 전혀 쓰지 않고** 키보드만으로 "결제완료"만 걸러본다.
- **시작 지점**: 결제 내역 화면. **이 태스크 동안 마우스·터치를 사용하지 않는다.**
- **성공 기준** — ★ **필터가 열리지 않는 것이 재현 성공이다**:
  1. **Tab**을 눌러 결제상태 필터까지 포커스를 이동시킨다. 포커스가 그 요소에 실제로 닿는지, **포커스 표시(테두리)가 보이는지** 기록한다.
  2. **Enter**를 누른다 → 필터가 열리는가.
  3. **Space**를 누른다 → 필터가 열리는가.
  4. **↓(아래 방향키)**를 누른다 → 필터가 열리는가.
  5. 2~4가 **모두 안 열리면 RSK-003 재현 성공**(원장 등재 blocker `br01-r04-D27` — 트리거가 `<input readonly>`라 키보드로 조작 불가).
  6. 그다음 **마우스로는 열리는지** 확인해 대조한다(마우스로만 열리면 "마우스 필수" 확정).
  7. 마우스로 연 뒤에는 **옵션 선택이 키보드로 되는지** 확인한다(옵션은 실제 버튼이라 열리기만 하면 될 수 있음).
  8. **"기간 전체" 필터는 클릭해도 옵션이 없는 별개 이슈**(RSK-016)이므로 이 재현과 **혼동하지 않고 따로 기록**한다.
- **관찰 포인트**:
  - 키보드만 쓰는 사용자에게 이 필터가 **기능적으로 존재하지 않는 것과 같다**는 점을 명확히 서술한다("불편하다"가 아니라 **"도달 불가"**).
  - Tab 순회 중 **포커스가 어디 있는지 눈으로 알 수 있는가**(포커스 가시성).
  - Tab 순서가 시각 순서와 일치하는가.
  - ※ 접근성 전담(`a11y-specialist`)과 항목이 겹쳐도 무방하다 — **여기서는 "기능에 도달할 수 없다"는 기능 관점**으로 기록한다.
- **커버 화면ID**: `S-BR01-1001-001`

### 메일 8종 — 문서 대조 전용

> ★ **공통 규칙(정지선 #9)**: "결제·유예·만료 메일(`1201-003~012`)은 **서버 이벤트라 UI로 트리거하지 않는다** — **문서 대조로만 검증**한다."
> 즉 아래 3개 태스크는 **화면을 조작해 메일을 발송시키지 않는다.** 실제 발송 시도(결제 완료·구독 취소 확정 등)는 정지선 #1·#2 위반이기도 하다.
> 🔴 **발송 구현 상태는 `[미확정]`이다 — "안 온다"도 "온다"도 전제하지 않는다.** 구 서술은 "발송 로직 자체가 서버 TODO"였으나, **원장 최신본(`BR01-r05.md:98`, 2026-07-28)은 "메일 발송 스텁+트리거 10건 배선 완료"**를 명시해 정면 충돌한다(02b §5-3).
> - 따라서 **"메일이 안 온다"를 자동으로 오탐 처리하지 않는다.** 이 3개 태스크는 애초에 **UI로 메일을 트리거하지 않으므로**(정지선 #9) 수신 여부를 검증 대상으로 삼지 않으며, **검증은 문서 대조로만** 한다.
> - **실발송 가능성이 생겼다는 사실은 정지선 #9를 더 엄격히 지켜야 할 이유**다 — 메일을 보려고 결제·구독취소를 실행하는 것은 **정지선 #1·#2 위반이자 실메일 발송**으로 이어진다.
>
> **★ 메일 문서를 열기 전에 반드시 알아야 할 4가지(storyboard 8건 전수 확인)**
> 1. **메일 제목(subject) 문구가 8건 모두 문서에 없다.** 문서에 있는 것은 **본문 헤드라인**뿐이다. → **"메일 제목이 적절한가"는 검증 항목으로 쓰지 않는다**(기준이 없다). 검증 가능한 것은 **본문 헤드라인 · 정보 필드 · 이용상태표 · CTA 라벨/목적지** 4가지다.
> 2. **8건 모두 `route: 해당 없음`** — URL로 도달할 수 없는 서버 발송 산출물이다. 브라우저로 열 수 없는 것이 정상이다.
> 3. **발송 구현 상태를 명시한 문서는 `1201-010` 한 건뿐**이다(스파이크에서 새 창 미리보기 미구현). 나머지 7건은 구현 여부 언급 자체가 없다 → **"발송이 안 된다/된다"를 단정하지 않는다.**
> 4. **8건 모두 "디자인 이슈: 특이사항 없음"**이라 **a11y·색상대비 기재가 0건**이다. 아이콘(성공/실패/경고)이 상태를 표현하는데 **텍스트 병기 여부는 문서에 없다** → "색·아이콘만으로 상태를 전달하는가"는 **문서만으로 판정 불가**이며, 판단하려면 실제 템플릿 HTML이 필요하다. 문서 대조 단계에서는 **`[미확인]`**으로 남긴다.

#### T25. 【문서 대조】 결제 결과 메일이 사용자에게 무엇을 알려주는지 대조한다

#### T27. 【문서 대조】 구독이 끝나가는 과정을 메일이 제대로 알려주는지 대조한다
- **목표**: 취소·만료 도래·만료 메일이 **화면 안내와 같은 말을 하는지**, 특히 **환불에 대해 오해를 만들지 않는지** 대조한다.
- **시작 지점**: 메일 템플릿 문서(`1201-010`·`1201-011`·`1201-012`) + 구독 취소 화면·완료 모달(T11·T12) 관찰 기록.
- **성공 기준** — 모두 **`[문서 대조]`**:
  1. **구독 취소 안내 메일(`1201-010`)**: 8건 중 **유일하게 사용자가 직접 유발**하는 메일이다(트리거 = `/my/product-cancel`에서 `DELETE /api/subscriptions/:id`(mode=expire) **성공**). 헤드라인 "구독이 취소되었습니다". 구독정보 **5필드**(사이트명·구독유형·취소 신청일·**서비스 이용 가능일**·서비스 상태="이용 가능 (취소 예정)"). 안내 = 만료일까지 정상 이용 · 종료 전 재시작 가능 · **즉시취소·환불은 1:1 문의**(BR-R-045). CTA = **[구독 플랜 보기] → `/pricing`**.
  2. ★ **정합성 대조 ①(이 태스크의 1급 검증)**: 이 메일은 **취소 완료 모달(`0801-003_pu01`)과 완전히 같은 이벤트에서 동시에 트리거**된다. 그런데 **모달**(T12)은 "구독 취소가 완료되었습니다"만 말하고 **종료일도 환불 여부도 없고**, **메일**은 **서비스 이용 가능일·환불 경로**를 말한다. → **같은 순간에 두 채널이 서로 다른 정보량**을 준다. 화면만 본 사용자는 **환불도 처리된 줄 오해**할 수 있다(RSK-027). 이것을 이슈로 명시한다.
  3. ★ **정합성 대조 ②(날짜)**: 문서가 **"취소일·만료일 표기가 서로 어긋나지 않게 같은 데이터 소스에서 생성할 것"**을 명시하고 있다. 모달과 메일이 **같은 날짜를 말하는지**를 대조 항목으로 남긴다(실데이터 도달 불가 시 `[미확인]`).
  4. **오탐 방지**: 목업의 "취소 후 메일 미리보기 새 창"은 **목업 전용 데모**이고 실제 앱은 **완료 alert만** 띄운다. → 페르소나가 **"취소했는데 메일 미리보기가 안 뜬다"고 보고하면 오탐**이다. 마찬가지로 **"즉시 환불 버튼이 없다"**도 정책상 정상(환불은 1:1 문의 수동 처리)이므로 결함이 아니다.
  5. **만료 도래 메일(`1201-011`)**: 헤드라인 "구독 만료가 다가옵니다". 트리거 = **만료일이 속한 결제주기 진입** — ★ **문서가 트리거 자체를 "추정"으로 표기**하고 **"마지막 달"이 D-30인지 결제주기 시작인지 `[미확정]`**이다. → **발송 타이밍을 합격 기준으로 쓰지 않는다.** 구독정보 **6필드**(사이트명·구독유형·결제주기·구독 시작일·구독 만료일·다음 결제 예정일). **연간 전환 시 30% 할인** 안내 포함. CTA = **[결제 관리 바로가기] → `/my/payments`**.
  6. **만료 메일(`1201-012`)**: 헤드라인 "구독이 만료되었습니다". 트리거 = **구독 만료일 당일(직후)**. 구독정보 **3필드**(사이트명·구독유형·만료일). 이용상태 = **Admin 중지 / Front 사용가능**, **만료 후 1개월** 경과 시 Front도 중단(BR-R-044). CTA = **[구독 갱신 바로가기] → `/pricing`**. → 이 "1개월"은 T26의 `1201-008`과 **동일 값으로 일관성이 확인된 유일한 수치**다(회귀 기준선으로 쓸 수 있다).
  7. ★ **혼동 위험 대조**: `1201-012`(만료)와 `1201-005`(결제 유예)는 **이용상태표가 똑같다**(Admin 중지 / Front 가능). 그런데 **원인은 전혀 다르다**(만료 vs 미납). → 사용자가 **두 메일을 구분할 수 있는가**를 검증 항목으로 남긴다.
  8. 세 메일의 **CTA 목적지**(`/pricing` · `/my/payments` · `/pricing`)가 **T2에서 확인된 "구매 경로 단절"과 부딪히지 않는지** 검토한다 — 메일이 "갱신·업그레이드하세요"라며 `/pricing`으로 보내는데 **그 페이지의 구매 CTA가 결제 화면으로 가지 않는다**면, 메일을 타고 온 사용자는 **돈을 내려다 또 막힌다**. 이 연쇄를 명시적으로 지적한다.
- **관찰 포인트**:
  - 취소한 사용자가 **"내 강의 사이트와 수강생 데이터는 어떻게 되나"**를 알 수 있는가.
  - `1201-011`은 **8건 중 유일하게 판촉 문구(연간 30% 할인)가 섞인 트랜잭션 메일**이다 — 만료 경고보다 판매 권유가 앞서 읽히는가(정보 vs 마케팅 균형). **발산형 관점**으로 "이 메일에 마케팅이 들어가는 게 옳은가"까지 검토한다.
  - `1201-011`이 **자동갱신 예정 사용자와 취소 예정 사용자에게 같은 템플릿**으로 나가는 것으로 보이는데(톤 분기 필요 여부 `[미확정]`), **이미 취소한 사용자가 "자동 갱신됩니다" 문구를 읽고 혼란**하지 않겠는가.
- **커버 화면ID**: `S-BR01-1201-010`, `S-BR01-1201-011`, `S-BR01-1201-012`

## 부록 C — 리포트 작성 시 지켜야 할 표기 (페르소나 필독)

1. **【재현】 태스크에서 막혔다면 "실패"가 아니라 "재현 성공"이다.** 리포트에 반드시 대응 위험ID(RSK-00N)를 적어 신규 이슈로 중복 등록되지 않게 한다.
2. **정지선에서 멈춘 태스크는 "미완주(정지선 준수)"**로 명시한다. "검증 실패"·"안 됨"으로 쓰지 않는다.
3. **데이터가 없어 못 본 것은 `[미확인]`(데이터 부재)**로 쓰고, "정상"으로도 "결함"으로도 쓰지 않는다.
4. **개발 단계 표식 6종**(`스테이징` 등)을 결함으로 올리지 않는다 — 대신 "사용자에게 어떻게 읽히는가"로 쓴다.
5. **자격증명·토큰을 절대 기재하지 않는다.** 계정은 "검수 계정(카드 등록용)"처럼 역할로만 지칭한다.
6. **모든 이슈에 증거를 붙인다** — 스크린샷 경로 / 콘솔 로그 / 재현 단계. 증거 없는 판단은 `[추정]`.
7. **금액·문구는 화면에서 본 그대로 인용**한다(임의 반올림·의역 금지).
8. **아래 4가지는 결함이 아니다 — 올리면 오탐이다**:

| 관측 | 왜 오탐인가 |
|---|---|
| "탈퇴 버튼을 눌러도 탈퇴가 안 된다" | 현 빌드는 실 삭제를 **의도적으로 미호출**(안전 조치). ※ 그래도 정지선 #3에 따라 **누르지 않는다** |
| "구독을 취소했는데 메일 미리보기 창이 안 뜬다" | 새 창 미리보기는 **목업 전용 데모**이고 실제 앱은 완료 안내만 띄운다 |
| "즉시 환불 버튼이 없다" | 즉시취소·환불은 **1:1 문의 수동 처리**가 정책(BR-R-045) |
| "사용량이 0으로만 나온다 / `사용량 미연동` 배지" | 집계 배치 미구현이 **문서화된 의도된 상태**(RSK-020) |

9. **결함으로 보이지만 실제로는 "미확정 정책"인 것**은 판정하지 말고 사실만 적는다 — 가격 카드↔비교표 수치 불일치(BR-R-035), 유예 3일·27일(BR-R-042), 연장 할인율 6개월 10%·12개월 30%(BR-R-041), 만료 도래 "마지막 달" 시점.

10. 🔴 **v1.1 신설 — "오탐표에서 빠진 것"을 오탐으로 처리하지 않는다.** v1.0의 오탐표에 있던 **"결제 이메일을 바꿨는데 저장이 안 된다 = 저장 EP 자체가 없어서 정상"** 행은 **삭제됐다.** 원장 최신본(`BR01-r05.md:98`, 07-28)이 **`0901-002/003` 구현 완료**를 명시해 **"저장이 안 되는 게 정상"이 더 이상 참이라고 말할 수 없기 때문**이다(02b §5-3, `EP 미비` 배지와 정면 충돌 → `[미확정]`).
    - **따라서 결제 이메일 저장 결과는 오탐 처리 대상이 아니라 `[관측 전용]` 대상**이다(T19-6·T21). **"안 되는 게 정상"이라고 배운 채 테스트하면 실결함을 정상으로 넘긴다** — 이것이 이번 검수의 1순위 지적이었다.
    - 같은 이유로 **메일 미수신도 자동 오탐이 아니다**(§메일 8종 공통 규칙). 수신 여부는 관측해 기록하고, **실발송 가능성이 있으므로 정지선 #9(주소당 2회)를 엄격 적용**한다.

11. **【재현】과 【회귀 스모크】의 판정 방향을 반대로 읽지 않는다.** 【재현】은 "막히면 성공", **【회귀 스모크】는 "정상이 성공"**이다. **RSK-004·005·006·007은 2026-07-28 수정·배포 완료**이므로 이들을 "찌를 곳"으로 다루면 **정상 화면을 확인하는 데 공수를 낭비**하거나 **정상을 실패로 오판정**한다(02b §5-1).
