## 1. 서비스 개요

- **서비스명**: 쏠쏠 (solsol) 브랜드사이트 — CREATOR PLATFORM
- **한 줄 설명**: 크리에이터가 자기 이름의 학습·멤버십 사이트를 만들고 플랜을 구독하는 올인원 플랫폼의 **공개 브랜드 사이트**(가입·로그인·요금제·구매·계정 관리 진입점).
- **대상 사용자**: 유튜브·SNS로 이미 팬을 가진 크리에이터, 온라인 강의를 팔고 싶은 1인 사업자/강사. 개발 지식이 없는 사람이 대다수다.
- **핵심 가치 제안**: "크리에이터를 위한 핵심 서비스만 모았습니다" — 개발자 없이 **내 도메인의 학습 사이트를 몇 분 안에 개설**한다.
- **이 묶음이 검증하는 것**: 그 가치에 도달하기 위한 **첫 관문 = 계정을 만들고, 들어오고, 못 들어올 때 복구하는 일**. 여기서 막히면 서비스의 다른 어떤 가치도 사용자에게 도달하지 못한다.

## 2. 테스트 환경

- **대상 URL**: `https://solsol-brand.pages.dev/` (`config/target.json` 의 baseUrl과 **일치해야 함 — 실행 전 설정 필요**)
  - ⛔ **현재 `config/target.json`은 다른 서비스(`http://localhost:8000` · "구글 파트너 정산")를 가리키고 있다**(`00_INDEX` §5 B-1, 실측). 이 상태로 실행하면 **전 페르소나가 엉뚱한 앱을 테스트하고 `guards`에 정지선 12항이 하나도 반영되지 않는다.** solsol-brand 전용 프로필 작성(권고: `config/target.solsol-brand.json`)이 **착수 선행 조건**이며, 이는 QA 리드/오너 결정 사항이다.
- **접근 방식**: 공개(가입·로그인·비밀번호 재설정은 비로그인 접근) + **스테이징 성격의 검수 빌드**
  - 로그인 화면 하단에 **"⚠ 임시 검수용 로그인 — 운영 로그인 아님"** 섹션(계정 버튼 10개)이 노출된다. 이는 검수 빌드(`NUXT_PUBLIC_SHOW_TEST_LOGIN` ON)에서만 렌더되는 **의도된 장치**이며 결함이 아니다(BR-R-079).
  - 백엔드 API: `https://solsol-brand-api.malgnsoft.workers.dev/api/*` (세션은 자체 `/api/session/*`)
- **테스트 계정**: **검수 계정(로그인 페이지 하단 임시 로그인 버튼)** 으로만 접근한다.
  - 계정/비밀번호 등 **자격값을 리포트·로그·스크린샷 캡션에 절대 기재하지 않는다**(정지선 #11). 직접 폼 로그인이 필요한 태스크는 `${ENV:QA_TEST_EMAIL}` / `${ENV:QA_TEST_PASSWORD}` 형태로만 지칭한다.
  - 계정 상태 다양성은 사실상 **"사이트 1개 보유(도탑) vs 사이트 0개(나머지 9)"** 두 종류뿐이다. 이 묶음은 로그인 착지 확인 외에는 계정 상태에 의존하지 않으므로, 페르소나별로 **서로 다른 계정 1개씩** 배정해 간섭을 피한다.
  - ⚠️ **계정 배정은 이 문서가 정하지 않는다 — 정본은 `00_INDEX-시나리오세트.md` §4-1(리드 배정 권고표)이다.** **페르소나 20인 vs 검수 계정 10개**라 1:1 배타 배정이 구조적으로 불가하므로, 리드는 **10인 × 2웨이브**(웨이브 사이 계정 회수·재배정)를 권고했다(`00_INDEX` §4-0). 묶음①의 배정 권고는 **P02·P08·P13·P17·P19 ↔ 뿌꾸·윤희·검수·미니·도탑(로그인 전용, 상태 변경 없음)**. **웨이브 분할 vs 페르소나 층화 축소는 QA 리드/오너 결정 사항**이며 집필자가 확정하지 않는다.
- **지원 뷰포트**: **모바일 390×844** / **PC 1440×900** 양쪽 모두 대상. 페르소나의 실제 기기에 맞춰 하나를 주로 쓰되, **T15(모바일 헤더 혼동)** 는 모바일 페르소나가 반드시 수행한다.
- **관찰 채널**: 화면 스크린샷 + 브라우저 콘솔. 단, 비로그인 전 화면에서 `POST /api/session/refresh` **401 콘솔 에러**와 로그인 후 화면의 **"Hydration completed but contains mismatches."** 경고는 **이미 문서화된 기존 현상**이므로 신규 이슈로 올리지 않는다(발생 여부만 기록).

## 3. 사전 조건 (Preconditions)

1. **시작 상태는 로그아웃(비로그인)** 이다. 이전 세션 쿠키가 남아 있으면 `/login` 접근 시 곧바로 `/my/sites`로 튕기므로(BR-R-011), 가입·재설정 태스크 전에 로그아웃 또는 새 브라우저 컨텍스트로 시작한다.
2. 🔴 **메일 발송 여부는 `[미확정]`이다 — 온다/안 온다를 전제하지 않는다.** 원장 내부가 서로 충돌한다: 한쪽은 **`auth.ts:565`·`auth.ts:727`에 발송 TODO 잔존**을 기록하고, 다른 쪽인 **원장 최신본 `BR01-r05.md:98`(2026-07-28)은 "메일 발송 스텁 + 트리거 10건 배선 완료"**를 선언한다(`_분석/02b` §5-3). 따라서 **어느 쪽도 사실로 단정하지 말고, 발송을 요청한 뒤 실제 수신 여부를 관측해 결과로 기록한다.**
   - **수신되지 않으면**: 그 사실을 기록하고 **"사용자가 이 상태에서 무엇을 겪는가"**(무한 대기·재발송 반복·이탈)를 관찰한다. **"메일이 안 오는 것이 정상"이라고 결론짓지 않는다** — 미수신이 실결함일 가능성이 열려 있다.
   - **수신되면**: 본문·링크 토큰 형식(`rid`·`t`)·색 대비·CTA를 그대로 캡처해 기록하고, 부록 A의 조건부 커버(메일 2종)를 **실검증으로 승격**한다.
   - ★ **실발송 가능성이 생겼으므로 정지선 #9(동일 주소 기준 시나리오당 최대 2회)를 엄격히 적용한다.** 메일이 실제로 나갈 수 있으므로 재발송 연타 테스트는 금지이며, 상한은 **시나리오 전체 합산**으로 센다(T2·T3·T5·T12·T13·T15 공통).
3. **정지선 #9 사전 인지(강조)**: "인증/재설정 메일 발송은 **동일 주소 기준 시나리오당 최대 2회**." 재발송 버튼 연타 테스트는 이 상한 안에서만 수행한다. **빌드가 실제로 발송하는지 여부에 의존하지 않고**(위 2항대로 발송될 수 있다) 상한을 지킨다. 상한에 걸려 멈춘 경우 **"정지선 준수: 미완주"**로 남긴다.
4. **정지선 #11 사전 인지**: "검수 계정 사용은 허용하되, 리포트에 **자격값(계정/비밀번호)을 절대 기재하지 않는다**(환경변수 참조로만)."
5. **가입 완주·재설정 완주는 "실수신 가능한 주소를 보유한 페르소나 전용 선택 태스크"다.** 대다수 페르소나는 실제 메일함이 없으므로 **전원에게 완주를 요구하지 않는다.**
   - **실수신 주소 보유 페르소나**: 그 주소로 가입/재설정을 시도한다. 성/이름에는 실명 대신 페르소나 식별자를 쓰고, **타인·운영자의 실제 주소를 입력하지 않는다.**
   - **미보유 페르소나(기본값)**: **T2·T3를 "인증코드 미수신으로 진행 불가"로 기록**하고, **T4~T7(비밀번호 규칙·이메일 형식·약관 동의·약관 모달) 폼 검증 경로로 우회**한다. T8(가입 완료 화면)은 `/signup-complete` 직접 진입으로 대체하고 **직접 진입임을 명시**한다. **T13(c)는 수행하지 않는 것이 기본값**이다(→ T13 정지선·부록 A #10 참조).
   - 이 분기는 **미완주가 아니라 설계된 경로**다. 통합 담당은 이를 "실패"로 집계하지 않는다.
6. 자동 저장된 비밀번호·아이디 기억하기 상태가 페르소나 간에 섞이지 않도록 **테스트마다 초기 상태를 맞춘다**.

  - **저친숙 사용자가 막힐 지점**: 온보딩 안내가 3스텝인지, 지금 어느 단계인지 알 수 있는가.
- **커버 화면ID**: `S-BR01-0301-003`
- **관련 규칙**: —
- **정지선**: 해당 없음(**사이트 생성은 이 묶음의 범위 밖** — [+ 생성하기]를 누르지 않는다. 묶음 ② 소관, 정지선 #10)

### T9. 내 계정으로 로그인해 서비스 안으로 들어간다
- **목표**: 로그인해서 내 작업 공간에 도달한다.
- **시작 지점**: 비로그인 상태의 어느 화면이든
- **성공 기준**: 로그인 후 **`/my/sites`("내 사이트 관리하기")** 에 착지하고, 헤더에 **"내 계정"** 메뉴가 나타난다.
- **관찰 포인트**:
  - 로그인 수단으로 **검수 계정(로그인 페이지 하단 임시 로그인 버튼)** 을 쓴다. 이 섹션의 경고 문구 **"⚠ 임시 검수용 로그인 — 운영 로그인 아님"** 이 사용자에게 **신뢰를 떨어뜨리는 요소로 읽히는지**(개발 단계 표식이 어떻게 읽히는가) 관찰한다 — 페르소나 관점에서는 결함이 아니라 **의도된 표식**이다(BR-R-079).
  - ★ **다만 이 섹션은 "의도된 검수 장치"인 동시에 GA 전 OFF 재배포가 필수인 릴리스 게이트 항목**이다(`0302-001` 체크리스트 · `_storyboard-qa3-completeness.md:85`). 프로덕션 URL에 **인증 우회 경로(계정 버튼 10개)가 공개 노출**된 상태이므로, **통합 담당은 이를 '오탐'으로 닫지 말고 'GA 게이트 미이행 리스크'로 승계**한다(`_분석/02b` §6-B 심각도 **상** 판정 · `00_INDEX` §5 B-5 오너 에스컬레이션).
  - **"아이디 기억하기"** 를 켜고 다시 방문했을 때 실제로 이메일이 채워지는가.
  - 로그인 직후 화면에서 **헤더 CTA가 여전히 "무료로 시작하기"** 로 남아 있는가(로그인했는데 가입 유도가 계속 보임 — 혼동 소지).
  - **`[회귀 스모크]` 세션 유지**(RSK-008 — `closed@r02-fix`, **이미 수정됨**): 로그인 후 `/my/sites`에서 **F5 하드 새로고침** → 로그인 화면으로 튕기는가. **새 탭에서 보호 URL 직접 입력**(`/my/payments` 등) 시 세션이 유지되는가. **찾아야 할 blocker가 아니라 "재발하지 않았는지"만 1회 확인**하는 항목이다. 정상이면 한 줄("회귀 없음")로 끝내고 시간을 쓰지 않는다.
  - **`[회귀 스모크]` 부모/자식 라우트 충돌**(RSK-005 — **2026-07-28 수정·배포 완료 + 실물 확인 완료**, `_분석/02b` §5-1): `/my/account` 와 `/my/account/billing-email` 이 **서로 다른 화면**으로 뜨는가(제목 "계정 관리" vs "결제 이메일 변경"). **이미 고쳐진 항목이므로 "막히면 성공"이 아니다** — 정상 분리가 기본 기대값이고, **어긋날 때만** 재발로 보고한다. *(두 화면의 기능 검증 자체는 묶음 ③ 소관 — 여기서는 라우팅 결과만 본다.)*
    - ※ 위 2건은 **회귀 스모크 시트(세션 시작 전 1인 1회, `_검수/06` 발산형 R5)로 이관하는 안이 검수에서 권고**됐다. 시트 채택 여부는 **QA 리드 결정 사항**이며, 미채택 시 이 태스크에서 1회 확인한다(20인 중복 확인 금지 — **묶음① 배정 페르소나 중 1인만 수행**).
- **커버 화면ID**: `S-BR01-0302-001`
- **관련 규칙**: BR-R-079
- **정지선**: **#11 — "검수 계정 사용은 허용하되, 리포트에 자격값(계정/비밀번호)을 절대 기재하지 않는다(환경변수 참조로만)."** 캡처에 계정 버튼 라벨이 찍히는 경우에도 이메일 주소·비밀번호가 노출되지 않도록 확인한다.

### T10. 잘못된 정보로 로그인을 시도하고, 왜 안 되는지 알아낸다
- **목표**: 로그인 실패 상황에서 사용자가 원인을 파악하고 복구 경로를 찾는다.
- **시작 지점**: 로그인 화면
- **성공 기준**: (a) **빈 아이디/빈 비밀번호**로 제출하면 각각 인라인 오류가 뜬다. (b) **존재하지 않는 이메일**과 **존재하는 이메일 + 틀린 비밀번호** 두 경우의 실패 메시지가 **서로 구분되지 않는 동일한 문구**다(계정 열거 방지, BR-R-010). *실패 문구 원문은 문서에 없음 `[미확인]` — 화면에 표시되는 문구를 그대로 기록한다.*
- **관찰 포인트**:
  - `[재현 태스크]` **레이트리밋 부재**(RSK-023 / br01-r02-D10, GA 조건 open): **틀린 비밀번호로 연속 5~6회** 로그인을 시도했을 때 **차단·캡차·지연·잠금이 전혀 없는지** 확인한다. 이는 알려진 미해소 항목의 **재현·영향범위 확인**이며, 6회를 넘겨 반복하지 않는다. 사용자 관점 관찰: 계속 실패하는 동안 서비스가 **"비밀번호를 잊으셨나요?" 같은 복구 유도**를 해주는가.
  - 실패 메시지가 **똑같아서 사용자가 원인을 못 찾는 부작용**은 없는가(보안 정책과 사용성의 충돌 — 판정하지 말고 체감을 기록).
  - 실패 상태에서 **[비밀번호 재설정]·[회원가입하기]** 링크가 눈에 들어오는가.
  - **저친숙 사용자가 막힐 지점**: 오류 문구가 폼 위쪽에만 뜨고 스크롤 밖이면 보이지 않는가. 에러아이콘 부재(D09)로 어느 칸이 문제인지 모르겠는가.
- **커버 화면ID**: `S-BR01-0302-001`
- **관련 규칙**: BR-R-010 · BR-R-005(placeholder "8자 이상" 표기 상충 재확인)
- **정지선**: **#11**(자격값 비기재). 실패 시도에 쓴 비밀번호 문자열도 리포트에 적지 않는다.

### T11. 로그인한 상태에서 다시 로그인 화면에 들어가 본다 / 로그인 전에 보려던 화면으로 되돌아온다
- **목표**: 이미 로그인한 사용자가 로그인 화면에 갇히지 않고, 로그인 전에 가려던 곳으로 자연스럽게 복귀한다.
- **시작 지점**: (a) 로그인 상태에서 주소창에 `/login` 입력. (b) 로그아웃 상태에서 보호 화면(예: 문의하기, 내 사이트 관리, 결제내역)에 먼저 접근 → 로그인 화면으로 보내진 뒤 로그인.
- **성공 기준**: (a) 로그인 상태로 `/login`에 접근하면 **즉시 `/my/sites`로 리다이렉트**된다(BR-R-011). (b) 비로그인 상태로 보호 화면에 접근하면 **`/login?next=<원경로>`** 로 이동하고, 로그인 후 **원래 가려던 화면으로 복귀**한다.
- **관찰 포인트**:
  - `/signup`은 이 게이트 범위 **밖**이다 — 로그인 상태에서 `/signup`에 들어가면 **회원가입 폼이 그대로 보이는가**(로그인 사용자가 이중 가입을 시도하게 되는 상황, RSK-014와 같은 계열).
  - **`[재현 태스크]` 헤더 "문의하기" 링크**: 로그인 상태에서도 href가 `/login?next=/inquiry` 라 **로그인 화면을 한 번 경유**한다. 사용자에게 "왜 또 로그인 화면이 뜨지?"로 읽히는 순간이 있는가(기능 자체는 자동 통과로 동작).
  - `[재현 태스크]` **오픈리다이렉트**(RSK-029, 심각도 **하**): `/login?next=//evil.example`·`/login?next=https://evil.example` 로 진입해 로그인했을 때 **외부 사이트로 나가지 않는지**만 확인한다(프레임워크가 차단하므로 정상이면 외부 이동 없음). **외부 도메인을 실제로 방문하지 않는다.**
  - `[재현 태스크]` **로그아웃 후 뒤로가기**(RSK-024): 로그아웃한 뒤 브라우저 **뒤로가기**로 보호 화면이 다시 보이는가, 새로고침 시 자동 재로그인되는가.
- **커버 화면ID**: `S-BR01-0302-001`
- **관련 규칙**: BR-R-011
- **정지선**: 해당 없음(외부 URL 실제 방문 금지 — 리다이렉트 발생 여부만 확인)

### T12. 비밀번호가 기억나지 않아 재설정을 요청한다
- **목표**: 로그인하지 못하는 사용자가 스스로 복구 절차를 시작한다.
- **시작 지점**: 로그인 화면(또는 로그인 실패 직후)
- **성공 기준**: 이메일을 입력하고 **[인증 메일 발송하기]** 를 누르면 **발송 완료 안내 화면**으로 이동한다. 실제 화면 문구: 제목 **"인증 메일 발송 완료 · 쏠쏠"**, 본문 **"인증 메일을 발송했습니다"**, **"인증 메일을 보내드렸습니다. 메일함을 확인해 주세요."**, **"메일이 도착하지 않은 경우, 스팸 메일함을 확인…"**
- **관찰 포인트**:
  - **미등록 이메일**로도 같은 완료 안내가 나오는가(계정 존재를 노출하지 않는 정책 BR-R-009 — 단 문서가 **"권장 정책"으로만 표기 `[추정]`** 하므로 합격선을 단정하지 말고 **실제 동작을 기록**한다).
  - 재설정 요청 화면은 **앱 전체에서 유일하게 폼 에러아이콘을 가진 화면**이다 — T4·T10의 다른 폼과 **오류 표현이 눈에 띄게 다른지** 비교한다(D09 영향 범위의 사용자 체감).
  - 완료 화면에서 **다음에 무엇을 할지**(메일함 확인·재발송·로그인 복귀) 경로가 있는가. 재발송 버튼이 있다면 **몇 번이든 눌리는가**(BR-R-004 제한 규정 없음 `[미확정]` — 확인만).
  - **메일이 실제로 도착하는가** — **수신/미수신 어느 쪽도 전제하지 않고 관측 결과를 기록한다**(사전조건 2, `[미확정]`). 도착하지 않으면 사용자는 이 화면에서 **무한 대기**하게 된다 — 그 체감을 기록하되 **"안 오는 게 정상"으로 닫지 않는다.** 도착하면 링크 진입(T13(c))으로 이어간다. **발송은 주소당 2회 상한(정지선 #9)**.
  - **저친숙 사용자가 막힐 지점**: "인증 메일"이라는 용어가 "비밀번호 바꾸기"와 연결되는가.
- **커버 화면ID**: `S-BR01-0302-002` · `S-BR01-0302-005` · `S-BR01-1201-001`(발송 트리거 지점)
- **관련 규칙**: BR-R-007(링크 유효 **30분**) · BR-R-009 · BR-R-004
- **정지선**: **#9 — "인증/재설정 메일 발송은 동일 주소 기준 시나리오당 최대 2회."** 미등록 이메일 검증분을 포함해 **주소별 2회**를 넘기지 않는다.

### T13. 메일 링크 없이 새 비밀번호 설정 화면에 들어가 보고, 정상 링크로는 어디까지 가는지 확인한다
- **목표**: 재설정 링크의 유효성 처리와 새 비밀번호 설정 절차를 확인한다.
- **시작 지점**: (a) 주소창에 `/password-reset-new` (**파라미터 없이**) 진입. (b) `/password-reset-new?rid=<임의값>&t=<임의값>` 처럼 **값만 있고 유효하지 않은** 링크로 진입. (c) **`[선택 태스크 — 실수신 가능 주소 보유 페르소나 전용]`** 메일을 실제로 수신했다면 그 링크로 진입. **미보유 페르소나는 (c)를 수행하지 않는 것이 기본값**이며(사전조건 5), 결과를 **`[미확인]` — "실수신 주소 미보유로 미수행"**으로 기록한다(실패가 아니다).
- **성공 기준**:
  - (a) `rid`·`t` 중 하나라도 없으면 **비밀번호 입력 폼이 아예 표시되지 않고** **"유효하지 않은 재설정 링크입니다"** 안내 + 재요청 경로(`/password-reset`) 유도가 보인다(BR-R-008).
  - (b) 형식만 갖춘 무효 토큰으로 제출하면 **성공으로 위장하지 않고** 오류가 표시된다.
  - (c) 정상 링크에서 새 비밀번호·확인을 넣고 완료하면 **완료 안내 모달("비밀번호가 재설정되었습니다" 계열)** 이 뜨고, 확인하면 **로그인 화면으로 이동**한다.
- **관찰 포인트**:
  - **비밀번호 강도 미터는 장식용**(BR-R-006)이다 — 미터가 "약함"인데도 통과되거나, "강함"인데 규칙 미충족으로 차단되는 **모순이 사용자에게 어떻게 읽히는지** 관찰한다(판정 자체는 미터와 무관한 것이 설계대로).
  - 두 필드의 **눈 아이콘(표시/숨김)** 이 각각 독립 동작하는가.
  - 확인 필드 **공란/불일치** 시 개별 오류가 뜨는가. 오류 표현에 **에러아이콘이 없는지**(D09 영향 화면).
  - 서버 미도달 시 **`MockBadge`** 가 노출되는가 — 이는 **의도된 개발 단계 표식**이다.
  - 링크 유효시간이 화면·메일에 **30분**으로 안내되는가(구값 "1시간"이 남아 있으면 기록).
  - (c) 경로를 밟지 못했다면 결과를 **`[미확인]` — "메일 미수신 또는 실수신 주소 미보유로 미완주"** 로 명시한다(성공/실패로 단정하지 않는다). **미완주가 기본값이며 이는 설계된 분기다.**

### T14. 유료 플랜을 사려다 로그인 화면을 만나는 경로가 살아 있는지 확인한다 `[재현 태스크]`
- **목표**: 구매 진입 전용 로그인 화면(`/purchase-login`)이 **사용자가 밟을 수 있는 경로로 존재하는지** 확인한다.
- **시작 지점**: (a) 가격 화면에서 유료 플랜의 **"구매하기"** 를 눌러 어디로 가는지 따라간다. (b) 주소창에 `/purchase-login` 직접 입력.
- **성공 기준**: **`[관측 전용 — 판정 없음]` 판정하지 않고 관찰한다.** 문서상 이 화면은 **"현재 고아"(진입 배선 없음, D02)** 로 기록돼 있다. 실측 결과 `/purchase-login` 은 **HTTP 302로 `/login?next=%2Fpurchase` 로 리다이렉트**된다 — 즉 **전용 로그인 화면이 렌더되는 것이 아니라 일반 로그인으로 넘겨진다**. 이 동작이 지금도 같은지 확인하고, **최종 착지 URL과 화면을 그대로 기록**한다.
- **관찰 포인트**:
  - `[재현 태스크]` **가격 CTA 오배선**(D02 / RSK-002): 가격 화면의 유료 **"구매하기"** 가 `/purchase`가 아니라 **`/login?next=/my/sites`** 로 가고, **로그인 상태에서도 동일**해서 최종 착지가 **내 사이트 목록**이 되는가. 즉 **정상 클릭 경로로는 구매 화면에 도달할 수 없는지**를 재현한다. *(구매 화면 내부 검증은 묶음 ③ 소관 — 여기서는 "로그인 관문을 통과해 어디에 떨어지는가"까지만 본다.)*
  - 로그인 후 `next=/purchase` 가 실제로 지켜지는가(구매 화면으로 가는가, 다른 곳으로 가는가).
  - **저친숙 사용자가 막힐 지점**: 돈을 내려고 눌렀는데 로그인 화면 → 사이트 목록으로 떨어졌을 때, 사용자는 자기가 뭘 잘못했다고 생각하는가.
- **커버 화면ID**: `S-BR01-0601-008`(유료구매 전용 로그인)
- **관련 규칙**: BR-R-011(`next` 처리)
- **정지선**: **#1** — 구매 화면에 도달하더라도 **[결제하기]를 누르지 않는다**. "카드 선택 + 약관 동의까지 진행해 [결제하기] 버튼이 활성화되는 것까지만 확인하고 클릭하지 않는다."

### T16. (보조) 마우스를 쓰지 않고 키보드만으로 가입·로그인·모달을 조작한다 `[재현 태스크]`
- **목표**: 손을 쓰기 어렵거나 스크린리더를 쓰는 사용자가 계정 관문을 통과할 수 있는지 확인한다.
- **시작 지점**: 회원가입 화면 / 로그인 화면 / 인증코드 안내 모달 / 약관 상세 모달
- **성공 기준**: **`[관측 전용 — 판정 없음]` 판정 전 관찰**이 목적이다. Tab만으로 모든 입력·버튼에 도달할 수 있고, Enter/Space로 실행되며, 모달 안에서 포커스가 빠져나가지 않는지 기록한다.
- **관찰 포인트**:
  - `[재현 태스크]` **포커스 트랩 부재**(RSK-011): 모달을 연 채 Tab을 계속 눌렀을 때 **포커스가 모달 밖 배경 폼으로 새는가**. 모달을 닫은 뒤 **포커스가 원래 트리거 버튼으로 돌아오는가**. 모달이 열린 채 **배경이 스크롤되는가**. (Esc 닫힘은 구현돼 있음)

  - **저친숙 사용자가 막힐 지점**: 키보드 사용자가 아니어도, **포커스가 어디 있는지 안 보이는 화면**은 모두에게 혼란을 준다.
- **커버 화면ID**: `S-BR01-0301-001` · `S-BR01-0301-002_pu01` · `S-BR01-C01` · `S-BR01-0302-001`
- **관련 규칙**: BR-R-077
- **정지선**: 해당 없음

### 이 묶음에서 특별히 갈라 봐야 할 것 — "결함 vs 의도된 미구현"

아래는 **결함으로 보고하면 오탐**이 되는 항목이다(원장에 의도된 상태로 기록됨). 관찰은 하되 **"미구현/보류(사유 있음)"** 로 표기한다.

> ⚠️ **이 표에 없는 것을 임의로 오탐 처리하지 않는다.** 특히 **메일 미수신은 오탐 목록에서 제외**됐다(아래 첫 행 — 판정 유보). 오탐표가 실결함을 은폐하는 것이 이 표의 최대 위험이다.

| 현상 | 실제 상태 |
|---|---|
| 인증코드·재설정 메일이 오지 않는다 | 🔴 **판정 유보 — 오탐이 아니다.** 메일 수신 여부는 **`[미확정]`**(원장 내부 충돌: `auth.ts` 발송 TODO 잔존 ↔ `BR01-r05.md:98` "메일 발송 스텁+트리거 10건 배선 완료", 2026-07-28). **오지 않으면 사용자 체감을, 오면 본문·링크 정합을 기록**한다. **"안 오는 게 정상"으로 닫지 말 것** — 실결함일 수 있다 |
| 로그인 화면 하단 "임시 검수용 로그인" 섹션 | **페르소나 관점에서는 의도된 검수 빌드 장치**(BR-R-079) — 결함 보고 금지. **단 통합 담당은 "GA 전 OFF 재배포" 릴리스 게이트 리스크로 승계**한다(T9 관찰포인트 ★ 참조) |

## 6. 제외 범위 (Out of scope)

1. **다른 묶음이 주관하는 화면**: 랜딩·플랫폼 소개·프로덕트·사이트 생성/목록·공지(묶음 ②), 가격·구매·결제·구독·카드·결제내역·계정관리·결제이메일(묶음 ③), 문의·약관 페이지 본문·에러/점검 화면(묶음 ④). 이 시나리오에서 이 화면들에 닿는 것은 **경로 확인 목적**뿐이다.
2. **약관 상세보기 모달(C01)의 부모 화면 중 "내 사이트 만들기(0401-001)" 쪽 사용**: C01 자체는 ①이 주관하되, 사이트 생성 플로우에서의 재사용은 **묶음 ②가 참조**한다.
3. **비가역 행위 전부**: 실결제 최종 승인, 구독 취소 확정, 계정 삭제 확정, 카드 삭제/대표 전환 확정, 사이트 [+ 생성하기], 실제 문의 접수. 이 묶음의 태스크는 어느 것도 이 지점에 도달하지 않는다.
4. **서버 가드 우회·API 직접 호출**: 개발자도구로 클라이언트 검증을 우회하는 시도(정지선 #5). 레이트리밋 확인(T10)도 **연속 5~6회 상한** 안에서만 수행한다.
5. **약관·개인정보 원문 전사**: 조문 구조·가독성·접근성만 본다(정지선 #12).
6. **실제 메일함 수신 확인이 불가능한 항목**: 메일 본문의 **레이아웃·색상 대비(1201-001·1201-002의 안내문 2.32:1 / 수신거부 링크 2.1:1 WCAG AA 미달)**, 링크 토큰 형식(`?token=${ENV:SECRET} vs 프론트가 요구하는 `rid`·`t`)의 정합. 메일을 수신하지 못하면 **`[미확인]`으로 명시**하고, UI에서 **"어떤 액션이 이 메일을 보내는가"** 까지만 검증한다. **메일 본문의 색 대비 검증은 페르소나 태스크가 아니라 템플릿/코드 리뷰 트랙 산출물**이다(`_분석/02b` §5-9 이관 지시). **단 실수신에 성공한 페르소나가 있으면 그 캡처는 1급 증거**이므로 반드시 첨부한다.
7. **"기존 유료 고객" 전제가 필요한 흐름**: 검수 계정 10개 중 **유료 플랜·카드 등록·결제 내역·문의 이력 보유 계정이 하나도 없어** 재현 자체가 불가능하다.
8. **실제 스크린리더(NVDA/VoiceOver) 실기 낭독 검증**: T16은 **키보드 조작·포커스 이동까지**만 다룬다. 실기 낭독은 별도 라운드 소관.
9. **관리자단(admin)·고객 프론트 사이트**: 브랜드사이트 밖이다.
