### 1.1 결제내역 필터 blocker — 구체 구현 방향 (네이티브 `<select>` vs `role=combobox`)

현재 코드(`payments.vue:177-192`)는 트리거가 `<input readonly>`이고, 열기/닫기는 `interactions.client.ts:113-129`의 전역 `document.click` 델리게이션 1건뿐이다. `readonly` 텍스트 input은 포커스는 받지만 Enter/Space에 클릭을 합성하지 않으므로(버튼·체크박스와 다른 네이티브 동작) 키보드만으로는 열 수조차 없다 — 옵션 자체는 실제 `<button>`(184행)이라 "일단 열리면" 키보드 선택은 가능하다는 점이 이 결함의 특이점이다.

**옵션 A — 네이티브 `<select>` 교체**
- 장점: Tab/Enter/Space/방향키/Esc 전부 브라우저가 무상으로 제공, 스크린리더 벤더 편차 없음, 접근성 리스크 0. 구현은 기존 `STATUS_OPTIONS` 배열을 `<option>`으로 매핑 + `v-model="statusFilter"`로 끝 — 실질 공수 XS~S.
- 단점: 커스텀 드롭다운(`.select-menu` 호버 스타일·아이콘 배치)을 브라우저 기본 UI로 대체해야 해 **디자인 일관성이 깨진다**(목업2 1px 이식 원칙과 정면 충돌 — br01 전체가 지켜온 "신규 색·컴포넌트 발명 금지"와는 결이 다르지만, 네이티브 select는 반대로 "디자인 이탈"이 되는 역설).

**옵션 B — `role="combobox"` 커스텀 위젯(ARIA 1.2 콤보박스 패턴)**
- 장점: 기존 비주얼(`.input-box--select`+`.select-menu`) 그대로 유지, 디자인 시스템 이탈 없음.
- 단점: `aria-expanded`·`aria-controls`·`aria-activedescendant`·옵션 `role="option"`·방향키 이동·Enter/Space 선택·Esc 닫기+포커스 복귀까지 전부 손으로 구현해야 하고, WAI-ARIA APG 콤보박스 패턴은 스크린리더 벤더별(NVDA/VoiceOver) 동작 편차가 커서 실기 테스트 없이는 "구현했다"고 안심할 수 없다. 실질 공수 L.

**권고**: 이 화면의 blocker를 즉시 해소하는 것이 1차 목표라면 **옵션 A(네이티브 select)**로 빠르게 막고, 동시에 열려 있는 D01(검색 실시간 필터)·D04(필터바 3종 복원) 리팩터링과 같은 작업에서 처리하는 것이 효율적이다. 디자인 시스템이 `.input-box--select` 패턴을 앞으로도 여러 화면에 반복 사용할 계획이라면, 중기적으로 공용 `AppSelect.vue`(옵션 B 방식)를 별도 스파이크로 구축해 결제내역·문의내역 등 커스텀 셀렉트 전체를 한 번에 교체하는 로드맵을 권고한다. **지금 당장 옵션 B를 이 화면 하나에만 손으로 구현하는 것은 투자 대비 비효율**(공용화 없이 화면당 재구현하면 L 비용을 화면 수만큼 반복).

| S-BR01-1201-001 비밀번호재설정 인증메일 | 이메일 | 부분가능 | 정책 충돌(1시간→30분) 서술은 상세하고 최종값 명확하나, 핵심 선행조건("실 메일 미발송, `auth.ts:727` TODO 잔존")이 문서 하단에 묻혀 눈에 안 띔. **더 중요한 문제**: 이 문서의 "디자인 이슈: 특이사항 없음"은 실측과 어긋난다 — 실제로는 색상 대비 결함(#AAAAAA 2.32:1, #B3B3B3 2.1:1)이 있는데(QA3 문서에서만 확인 가능), 이 storyboard 문서만 보면 해당 결함의 존재 자체를 알 수 없음 |

### 추가 확인 — "누더기" 지목 3개 문서 재검토

과제에서 특정 지목한 `S-BR01-0801-003`(구독취소, 위 `_pu01`의 부모)·`S-BR01-1201-001`(위 표에 포함)·`S-BR01-1201-005`(결제유예메일)를 별도로 재확인:

- **S-BR01-0801-003**(부모) — `_pu01`과 동일하게 ID 계보 설명("`S-BR01-0801-001_pu01`이라는 구 참조")이 "정책" 섹션의 절반 이상을 차지한다. 실제 개발 대상(구독 취소 폼 자체의 기능·분기)은 앞부분 4줄로 충분히 명확한데, **부모/자식 문서 양쪽에 거의 동일한 ID 계보 설명이 중복 기재**돼 있다 — 어느 한 문서(자식 `_pu01`)에만 두고 부모는 "자세한 계보는 `_pu01` 참조"로 축약해도 될 위치.
- **S-BR01-1201-001** — 위 표 참조. 유일한 실질 문제는 "디자인 이슈: 특이사항 없음"이 QA3 실측과 어긋난다는 점(자체 모순은 아니고, 검토 시점 차이로 인한 정보 격차).
- **S-BR01-1201-005** — 정정 이력(005→007→008 라이프사이클 분리)이 있으나 "정정, 2026-07-27 2차 QA — §정책 참조"처럼 **어디를 봐야 정정 근거가 나오는지 셀프 참조로 명확히 안내**하고 있어 실제로는 헷갈리지 않았다. 세 문서 중 이 문서만 "정정이 잘 정리된 사례"로 평가한다 — "누더기"라는 지적은 0801-003·1201-001 두 문서(ID 계보 중복·검토 시점 격차)에 더 해당한다.

**공통 패턴**: 15개 표본에서 발견된 "헷갈리는 지점"은 대부분 **정정/이력 설명이 실제 구현 내용보다 길어서 개발자가 "무엇을 고쳐야 하는지"를 찾는 데 시간이 걸리는 것**이지, 정보 자체가 틀린 경우는 거의 없었다(예외: `S-BR01-1201-001`의 "특이사항 없음"만 유일하게 실측과 불일치). API 계약 자체(로그인·비번재설정·도메인체크·결제내역)는 3차 API QA의 확인대로 정확했고, 파일:라인 근거도 대체로 검증 가능했다 — "찾기 쉬운가" 관점에서의 감점 요인은 **반복 인용되는 각주(D09 8개 화면 목록, ID 계보)가 본문 서두가 아니라 문서 중후반에 배치되어 실제 작업 지시(무엇을 어떻게 고칠지)와 뒤섞이는 배치 문제**다.

## 3. 컴포넌트 재사용성 검증 (코드 실측)

storyboard가 반복 주장하는 "11개 모달이 실제로는 3개 공용 컴포넌트만 쓴다"·"공용 컴포넌트 1곳 수정으로 여러 화면 일괄 해소"를 grep으로 검증한 결과, **주장은 코드 레벨에서 정확했다**.

```
useModal (SolsolModal 렌더 트리거) 사용처 — 10개 페이지 파일에서 총 29개 호출 지점
AccountDeleteModal 사용처 — my/account.vue 1개 파일만
TermsModal 사용처 — signup.vue 1개 파일만(이용약관·개인정보·마케팅 3종 콘텐츠를 slot으로 주입해 재사용)
modal-overlay 클래스 직접 사용 — 3개 컴포넌트 파일 자신뿐(inline 복붙 0건)
window.confirm/window.alert 직접 호출 — 0건
```

- **SolsolModal.vue**(단일 컴포넌트, `app.vue`에 1회 마운트 + 전역 싱글턴 상태 `useModal.ts`)가 alert/confirm 계열 9종(도메인중복확인·도메인사용중안내·인증코드발송×2·카드관리 3종(대표카드등록확인/카드삭제확인/카드최소1개유지안내/대표카드삭제불가안내 — 실제로는 4종)·구독취소완료안내·파일용량초과안내·구독취소컨펌)을 전부 렌더한다 — **여기에 포커스 트랩/복귀/스크롤잠금을 추가하면 정말로 한 곳 수정으로 이 9종 전부가 해소된다.**
- **AccountDeleteModal.vue**는 계정삭제 확인 1종 전용의 별도 컴포넌트다 — storyboard 자신(`S-BR01-0901-001_pu05` 문서)도 "공용 컴포넌트 수정만으로는 해소 안 됨, 별도 작업 필요"라고 정확히 명시하고 있어 **과신하지 않는다.**
- **TermsModal.vue**는 이용약관/개인정보처리방침/마케팅 3개 콘텐츠를 하나의 컴포넌트가 slot으로 처리한다 — "11개 모달" 개수 안에 잡히는 3종이 실제로는 컴포넌트 1개다.
- 위 3개 컴포넌트 외에 `.modal-overlay`/`.modal-card`/`.terms-modal` 클래스를 인라인으로 복붙한 화면은 0건 — "산발 구현 없음"이라는 컴포넌트 주석(TermsModal.vue:6-8, AccountDeleteModal.vue:5-8)의 자기 서술도 실측과 일치했다.

**결론**: 접근성 수정 작업을 배정할 때 "SolsolModal 1곳만 고치면 9종 모달이 끝난다"는 storyboard의 전제는 신뢰해도 된다. 다만 실제 작업량 산정 시에는 **AccountDeleteModal·TermsModal 2곳을 별도로 반드시 포함**해야 한다(총 3개 파일 수정 — storyboard도 이 구분을 이미 정확히 알고 있었다).

## 요약

접근성 10건 중 저비용·고임팩트 우선순위: 케밥 ESC·aria-expanded(전역 플러그인 1곳, XS~S) → 더보기 Space·purchase-card role=alert(각 1줄, XS) → 이메일 색상 대비 2건(hex 교체, XS) → 모달 스크롤잠금·포커스복귀(SolsolModal 1곳+2곳, XS~S) → 포커스 트랩(3곳, S) → 필드 에러 aria-describedby(6개 폼, M, 가장 반복노동 큼) → 결제내역 필터 키보드 접근(구조변경, L, 최후순위·네이티브 select로 즉시 해소 후 중기 공용 combobox 로드맵 권고).

개발착수 가능성: 15개 표본 중 로그인·인증코드발송모달(회원가입)·계정삭제확인·파일용량초과안내·문의내역목록·결제내역·시스템에러·404 8건 "가능", 나머지 7건 "부분가능"(불가능 0건, 카드등록만 경계). 감점 요인은 정보 오류가 아니라 **정정/이력 설명이 본문보다 길어 실제 작업 지시를 찾기 어려운 배치 문제**(D09 8개 화면 목록 3회 반복 인용, ID 계보 설명 중복)이며, 유일한 실측 불일치는 비밀번호재설정 인증메일 문서의 "디자인 이슈: 특이사항 없음"(실제로는 색상 대비 결함 존재, QA3에서만 확인 가능).

컴포넌트 재사용성: storyboard의 "3개 공용 컴포넌트로 11개 모달 커버" 주장은 grep 실측으로 정확히 확인됨(SolsolModal 9종 단일 컴포넌트, AccountDeleteModal·TermsModal 각 전용/재사용 1개씩, 인라인 복붙 0건, window.confirm/alert 0건) — 과신 없이 정직하게 서술된 문서였다.

핵심 발견 3~5개:
1. 결제내역 상태 필터는 실제로 키보드로 절대 열 수 없는 확정 blocker(코드 구조상 명백) — 네이티브 `<select>` 교체가 즉시 해소책, `role=combobox`는 디자인 일관성은 지키나 화면당 재구현하면 비효율적이라 공용 위젯화가 선행돼야 함.
2. 모달 접근성 결함(포커스 트랩/복귀/스크롤잠금) 수정은 storyboard 주장대로 SolsolModal 1곳에서 9종이 해소되지만, AccountDeleteModal·TermsModal 2곳은 반드시 별도 작업으로 잡아야 함 — storyboard 자신도 이 구분을 이미 정확히 인지하고 있었다.
3. D09(폼검증 에러아이콘 누락) 8개 화면 목록이 storyboard 여러 문서에 통째로 반복 인용되는 패턴이 "찾기 쉬움"을 해친다 — 정확하지만 비효율적인 문서화 방식.
4. 이메일 템플릿의 색상 대비 결함(2건)은 storyboard 문서 자체엔 전혀 언급이 없고 QA3 별도 문서에만 존재 — "디자인 이슈: 특이사항 없음"이라는 storyboard의 서술을 그대로 믿으면 이 결함을 놓친다.
5. 필드별 에러의 `aria-describedby` 부재는 6개 폼 전체 공통이지만 공용 `FormField` 컴포넌트가 없어 "한 곳 수정" 해소가 불가능한 유일한 접근성 항목 — 근본 해결(공용 컴포넌트화)은 별도 리팩터링 프로젝트급 선행 투자가 필요하다.
