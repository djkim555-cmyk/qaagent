# BR01 storyboard 3라운드 QA — 테크니컬 라이팅 품질

> 정본: [`docs/storyboard/README.md`](../../storyboard/README.md). 페르소나 = **글쓰기 품질**만 검사(정확성·정책 정합·형식 규칙은 QA1/QA2/QA3의 다른 페르소나가 이미 검토 — `_storyboard-qa-*.md`·`_storyboard-qa2-*.md`·`_storyboard-qa3-{screenid,regression,policy,security}.md`).
> 대상: `docs/storyboard/solsol-brand/` 45개 전수 정독(우선 지정 16개 + 나머지 29개 전량, 표본이 아니라 전건 확인).
> 관점: 명료성 · 정보 구조(사실/이력/미결 분리) · 어조·시제 일관성 · 독자(신규 개발자) 관점 3초 파악 · 중복·군더더기.
> 정리: 또박(테크니컬 라이터) · 2026-07-27 (KST)

## 0. 총평

45개 문서는 헤더(route·정리·최종수정·상태) + 5섹션(기능 정의 → 표시 조건·상태·분기 → 정책 → 디자인 이슈 → 이식 주의 종합) 템플릿을 **예외 없이 준수**하고 있고(QA-format 라운드에서 이미 확인), 어조도 **개조식 명사형 종결로 45개 전부 일관**(narrator 문장에서 "-습니다"체 사용 0건, `니다.` 패턴은 전부 인용부호 안 UI 카피뿐 — grep 실측 확인)되어 있다. 문서 구조 자체는 전반적으로 우수하다.

문제는 형식이 아니라 **내용 밀도** 쪽에서 발생한다: 여러 차례(2026-07-15 회수 → 2026-07-27 재배정 → 2026-07-27 2차 QA 발견 → 2026-07-27 2차 QA 정정)에 걸쳐 정정이 쌓인 문서는 "정책" 섹션 한 문단 안에 **사실·이력·미결 이슈가 뒤섞인 긴 문장**이 생겨, 신규 개발자가 "지금 뭘 구현해야 하는지"를 바로 못 찾고 이력을 먼저 읽어야 하는 경우가 있다.

## 3. 중복·군더더기

1. **`S-BR01-0801-003` ↔ `S-BR01-0801-003_pu01`**: 구ID(`0801-001_pu01`) 유래·통합 권고 문단이 두 파일에 **거의 동일한 문장으로 중복 서술**(0801-003 L17 vs pu01 L15). README 방침("횡단 요약 파일 금지")을 지키려는 의도는 이해되나, 이 경우는 요약 파일이 아니라 부모-자식 1:1 관계라 — 부모(0801-003)는 "이력·통합 권고는 자식 문서(pu01) §정책 참조" 한 줄로 줄이고, 전문은 pu01에만 남기는 편이 유지보수 시(한쪽만 고치고 한쪽을 빠뜨리는 사고) 위험을 줄인다.
2. **`S-BR01-0401-001_pu01` ↔ `S-BR01-0401-001_pu02`**: "사용 가능/사용 중" 2상태 분리는 타당하나(매핑표 근거 명시), 정책 소스 안내문(L4)·API 연동 정정 문단(L10-11)·디자인 이슈 표 2행(L25-26)이 **글자 단위로 거의 동일하게 두 파일에 반복**된다. 저자도 "각 파일이 독립적으로 읽혀야 하므로 중복 기재했다"고 명시적으로 밝혀 의도된 트레이드오프임은 확인했다 — 다만 도메인 표기(`.solsol.com`→`.solsol.live`) 같은 **사실이 바뀌면 두 파일을 항상 함께 고쳐야 하는 부채**가 생긴다는 점은 명확히 표시해 둘 필요가 있다(예: 두 파일 상단에 "이 문단은 pu02와 동기화되어야 함" 상호 참조 각주 추가 권고 — 이미 서로 링크는 있으나 "동기화 대상 문단"이라는 명시는 없음).
3. **경미한 반복(문제 아님)**: 이메일 템플릿 12종(`1201-001~012`)이 매 파일 "2026-07-27 오너 재승인 재배정(근거 = `BR01_화면ID_매핑표.md` §6.3)"을 반복 — 이건 각 파일이 독립적으로 읽혀야 하는 정당한 반복(출처 각주)이라 군더더기로 보지 않음.

## 4. 일관성(어조·시제) — 발견 없음

- narrator 문장 종결: 45개 전부 개조식(명사형/`-음`·`-함`·`-임`·`-다` 혼용은 절 유형에 따른 정상 변주, "-습니다"체 0건, `그렙 "니다\.$"` 결과 0건).
- 시제: 과거 확정 사실(`~됨`·`~했다`)과 현재 상태(`~다`) 구분이 문서 전반에서 일관 — 정정 서술도 "~였으나 → 현재는 ~다" 패턴을 공통적으로 사용.
- 인용된 UI 카피(따옴표 안)만 "~습니다"·"~해요"체가 등장하며, 이는 실제 화면 문구이므로 지문과 혼동 소지 낮음(따옴표로 명확히 구분됨).
- **결론**: 어조·시제 축은 45개 전체에서 문제 발견 0건 — 별도 정리 불필요.

## 5. 독자(신규 개발자) 관점 — 3초 파악 안 되는 문서 유형

- **유형 A(단순 화면·정정 없음)**: 9001-001/002/004/005, 0701-001_pu01, 0901-001_pu01, 0801-002 등 — 헤더+5섹션만으로 3초 내 "무엇을 구현할지" 파악 가능. 문제 없음.
- **유형 B(단일 정정 1건)**: 대부분의 이메일 템플릿(1201-002~012), 0601-001, 0401-002 등 — `**[정정]**`/`**값·수치(확정)**` 볼드 마커가 앞머리에 있어 3초 파악 가능.
- **유형 C(정정 2건 이상 + 구ID 이력 서술)**: 0801-003, 0801-003_pu01, 1201-001, 1201-005, 0401-001_pu01/pu02 — 결론이 문단 중간~끝에 있어 **전체 문단을 다 읽어야 "지금 뭐가 맞는지" 확정**된다. 위 §1·§2가 지목한 파일과 동일 — 신규 개발자가 헤매기 쉬운 문서 유형은 이 5(6)건으로 좁혀진다.
- **참고(구조적 한계, 이번 라운드 수정 대상 아님)**: 이메일 라이프사이클 체인(005→007, 011→012→008)과 LPU 모달 분기 우선순위(pu02/pu03/pu04)는 각 파일이 서로를 프로즈로 교차 참조하는 구조라, 전체 흐름을 파악하려면 3~4개 파일을 열어야 한다. `README §2`가 횡단 요약 파일을 명시적으로 금지하고 있어 이번 권고에서는 다루지 않지만, 정책팀이 필요하다고 판단하면 화면ID 매핑표(`BR01_화면ID_매핑표.md`) 안에 체인 순서를 표로 요약하는 것도 검토할 만하다(횡단 "요약 storyboard 파일"이 아니라 이미 존재하는 매핑표 확장이라 방침 위반 아님).
