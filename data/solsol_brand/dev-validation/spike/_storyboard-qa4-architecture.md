## 총평 — 3개의 서로 다른 성장통

이 문서 세트는 3개의 독립된 구조 문제를 동시에 안고 있고, 지금까지의 라운드는 이걸 "개별 결함"으로 다뤄와서 근본이 안 잡혔다.

1. **가변 식별자(mutable identifier) 문제** — 화면ID 문자열이 시점마다 다른 뜻을 가진다(§1).
2. **색인 부재의 트레이드오프 비용** — "화면1=파일1, 횡단 요약 금지"가 71개 규모에서 한계에 도달(§2).
3. **정정 누적을 담을 그릇이 없음** — 템플릿에 이력 전용 슬롯이 없어 본문이 누더기가 된다(§3).

여기에 코드 레벨 2건(모달 a11y 로직 3중복 §4, screenDocs.ts 수동 매핑 포화 §5)이 겹친다. 아래는 5개 항목 각각의 결정이다.

## 항목 1. 화면ID 체계의 구조적 건전성 — **결정: 화면ID를 불변(append-only)으로 규약화, 문자열 재사용 금지**

### Finding
§6 번복(2026-07-15 "비대상" → 2026-07-27 "재배정")이 만든 문제의 본질은 "번복 자체"가 아니라 **화면ID 문자열이 시점에 따라 다른 실체를 가리키는 가변 식별자가 됐다는 점**이다. 매핑표 실측 근거:

- `S-BR01-0801-001_pu01`: 원래 "구독취소 완료 LPU"(§3.3) → §6.2 #2에서 "재사용 불가"로 판정 → 신규 `0801-003_pu01`로 이동. 그런데 §6.4가 "두 ID가 동일 콘텐츠, 통합/분리 미정"이라 **한 실체에 두 살아있는 ID가 공존**(qa3-completeness 표A #9와 동일).
- `S-BR01-0901-001_pu04`: 07-15엔 "계정삭제 컨펌"의 회수된 옛 번호 → 07-27 재배정에서 **같은 문자열 `_pu04`가 "대표카드 삭제불가 안내"라는 전혀 다른 화면**에 신규 배정됨(계정삭제는 `_pu05`로 밀림, §6.2 #6·#7). 라이팅 QA가 "자기 언급적 혼동"으로 지목한 바로 그 지점(`_storyboard-qa3-writing.md` 2-3).
- `S-BR01-1201-*`: 이메일 12건이 구 무효 ID(3개 depth 산재)와 신 ID(1201 단일 depth)가 1:1이 아니게 재매김(§6.3) — `1201-001`이 07-15엔 "서비스생성", 07-27엔 "비밀번호재설정".
- `screenDocs.ts:525` 스테일 매핑(`POLICY_B_SITES`), `:508~510`의 `POLICY_B_ACCOUNT` 전용 스테일 매핑이 재배정으로 "우연히 legitimize"됨(§6.2 비고) — **정합이 아니라 우연**이다.

같은 문자열이 시점 T1과 T2에 다른 의미를 갖는 것은 데이터베이스로 치면 PK 재사용이다. `git blame`·과거 커밋·외부 링크(예: `docs/dev-validation/br01-r04.md`의 결함 참조)가 전부 조용히 깨진다. qa3가 "죽은 참조"라 부른 것이 정확히 이 증상이다.

### Decision (아키텍트 결정)
**화면ID는 불변·append-only 자산으로 규약화한다. 회수된 ID 문자열의 재사용을 금지한다.** 구체 규칙 3개를 매핑표 §1(채번 규칙)에 신설:

1. **재사용 금지(no-recycle)**: 한 번 발급된 `_pu##`·depth 번호는 회수되더라도 다른 실체에 재배정하지 않는다. 다음 빈 번호로만 전진한다. (`_pu04`를 계정삭제에서 회수했으면 대표카드삭제불가는 `_pu06`을 쓴다 — 番호가 비어 보여도 건너뛴다. 연속성보다 안정성 우선.)
2. **deprecated 마킹 규약**: 매핑표에 `상태` 컬럼을 `active | deprecated | superseded-by:<신ID>` 3값으로 공식화. §6처럼 "원본 보존 + 새 절 추가" 방식은 유지하되, **죽은 ID는 지우지 말고 `deprecated` 행으로 남긴 뒤 `superseded-by`로 후속 ID를 명시**한다. 지금은 이 링크가 산문으로만 존재(§6.4)해 기계적으로 추적 불가.
3. **번복 이력 = 매핑표 단일 지점**: 화면ID 변경 이력은 storyboard 개별 파일이 아니라 **매핑표 §6 형식(전후 대조표)에만** 누적한다. 개별 파일은 "현재 ID"만 들고, "왜 바뀌었나"는 매핑표를 링크한다(§3의 이력 분리 원칙과 정합).

> **근거**: 향후 5차·6차 번복이 또 올 것이 거의 확실하다(3라운드 동안 매 라운드 번복 발생). 그때마다 문자열을 재사용하면 혼란이 지수적으로 는다. append-only + deprecated 마킹은 번복이 몇 번 오든 "이 ID가 지금 무엇이고 과거에 무엇이었나"를 O(1)로 답하게 한다. 비용은 번호가 듬성듬성해지는 것뿐 — ID는 사람이 외우는 게 아니라 조회하는 것이므로 수용 가능.

## 항목 2. 문서 구조 확장성 — **결정: "화면1=파일1"은 유지, "횡단 요약 금지"(README §2)는 개정**

### Finding
"화면1=파일1"은 좋은 결정이고 71개, 나아가 크리에이터+브랜드 전체(수백 화면)에서도 유지 가능하다 — 파일이 독립적으로 읽히고, 소유·경합 경계가 화면 단위로 깔끔하며(README §0), 병렬 편집에 강하다. 이 축은 건드리지 않는다.

문제는 **README §2가 "횡단 요약 파일을 두지 않는다(중복 허용)"고 명시적으로 못박은 부분**이다. qa3-completeness가 이 트레이드오프의 실제 비용을 2건 실증했다:
- D07을 초안이 "3화면 공통"으로 오기재(실제 2화면) — 색인이 없어 카운트를 눈으로 세다 틀림.
- D09는 "완전한 그림을 보려면 미커버 화면까지 봐야 하는 역설" — 횡단 결함 1건이 몇 화면을 건드리는지 한 곳에서 확인 불가.
- 결정적으로, **71개 우주 중 이번 배치에서 제외된 27개가 "의도적 제외"인지 "실수 누락"인지 구분할 문서가 없다**(qa3 §1-B: 71−44 차집합을 직접 계산해야만 얻어짐).

45개에서는 "감당됐다"가 아니라 "티가 안 났다"에 가깝다. 71개, 특히 제품 2개 합산 규모에서는 색인 부재가 "누락을 발견할 수 없는" 구조적 실명(blind spot)이 된다. 화면 단위 문서화는 "이 화면에 뭐가 있나"(수직)엔 강하지만 "이 결함/이 상태가 어느 화면들에 걸치나"(수평)엔 원천적으로 답을 못 한다.

### Decision (아키텍트 결정 — README 개정 제안)
**storyboard 폴더 안에는 색인을 두지 않는다는 원칙은 유지하되, README §2를 개정해 "경량 색인은 다른 트랙(매핑표·결함원장)에 두는 것을 허용/의무화"로 명문화한다.** 즉 "요약 금지"를 "storyboard 폴더 내 요약 storyboard 파일 금지"로 좁히고, 두 개의 경량 색인을 의무화:

1. **배치 스코프 색인(신설, 매핑표에)**: 71개 우주에서 "이번 배치 포함 N / 제외 M + 제외 사유(레거시/저우선/후속예정)"를 매핑표에 표 1개로 박는다. qa3 개선제안 #1과 동일. 이건 "요약 storyboard"가 아니라 채번 스펙의 일부이므로 §2 방침 위반이 아니다.
2. **횡단 결함 색인(신설, 결함원장 `br01-r04.md`에)**: "결함ID → 영향 화면 수·목록" 표 1개. qa3 §5 #5와 동일. 원장은 이미 결함 단위 문서이므로 이게 자연스러운 자리다.

> **근거**: 화면 중심 문서(수직)와 결함/상태 중심 색인(수평)은 **서로 다른 관심사**라 한 파일에 억지로 합칠 게 아니라 각자 제 트랙에 둬야 한다. storyboard=수직 정본, 매핑표·원장=수평 색인. 이렇게 나누면 "화면1=파일1"의 장점(경합·독립성)을 하나도 잃지 않으면서 색인 부재의 실명만 제거한다. README §2의 "중복 허용" 문장은 그대로 두되(화면 파일끼리의 중복은 여전히 허용), "횡단 정보는 색인 트랙에 둔다"를 병기한다.

## 항목 3. 정정 누적 패턴 — **결정: 템플릿에 "## 정정 이력" 전용 섹션 공식 도입 (제안 아님, 결정)**

### Finding
qa3-writing이 "누더기" 5건(0801-003, 0801-003_pu01, 1201-001, 1201-005, 0901-001_pu05)을 지목했고, qa3-completeness §4가 "44개 중 40% 이상이 2회+ 수정, 정정이 정정을 참조하는 사례 발생"을 실측했다. 근본 원인은 명확하다: **템플릿(README §2)에 정정을 담을 슬롯이 없어서, 정정이 갈 곳이 본문 불릿 사이밖에 없다.** 그 결과 한 문단에 "사실 + 왜 바뀌었나 + 아직 미정 + 그 정정에 대한 재정정"이 뒤섞인다.

이건 개별 파일 5건을 다듬어 해결될 문제가 아니다. 4차·5차가 이어지면 정정은 계속 쌓이고, 5건이 15건이 된다. 개별 정리는 땜질이고, 구조가 정정을 흡수하도록 바꿔야 근본 해결이다. 허브의 다른 정본(`docs/history/` append-only, `br01-r04.md §8` "후속 정정" 전용 절)은 이미 이 패턴을 갖고 있는데 storyboard만 없다.

### Decision (아키텍트 결정)
**README §2 파일 템플릿에 최하단 "## 정정 이력" 전용 섹션을 공식 추가한다.** 규칙:

- 본문 5섹션(기능/표시조건/정책/디자인이슈/이식주의)은 **항상 현재 확정 사실만** 담는다. 과거형·취소선·"~였으나" 서술을 본문에서 뺀다.
- 정정이 생기면 본문은 새 사실로 덮어쓰고(overwrite), **한 줄을 "## 정정 이력"에 append**: `- YYYY-MM-DD (N차, 정리자): <무엇을 무엇으로> — 사유/근거 링크`.
- 화면ID 변경 이력은 여기 두지 않고 매핑표 §6을 링크한다(항목 1-3과 정합 — 이력의 단일 소유처 분리).
- **적용 시점**: 4차부터 신규·수정하는 모든 문서에 강제. 기존 누더기 5건은 **이번 4차 라운드에 리팩터**(qa3-writing이 이미 재배치안을 제시했고 사실관계는 검증 완료라 저비용). 나머지 39개는 다음에 그 파일을 만질 때 기회주의적 이관(big-bang 전수 리팩터 금지 — 비용 대비 효익 낮음).

> **근거**: qa3-writing은 "다음 라운드부터 권고"로 부드럽게 남겼지만, 아키텍트로서 더 강하게 간다 — **권고가 아니라 템플릿 규약**으로 박아야 한다. 권고는 지켜지지 않고, 지켜지지 않으면 6차엔 "정정 이력 섹션 없는 파일"과 "있는 파일"이 섞여 더 나빠진다. 템플릿 강제는 새 문서에 대해 비용이 0(그냥 섹션 하나 더)이고, 기존 5건 리팩터는 이미 분석이 끝나 있다. 지금이 4차라 44개뿐일 때가 이 규약을 넣을 마지막 저비용 시점이다.

## 항목 4. 컴포넌트 재사용 아키텍처 — **판정: "SolsolModal 한 곳 고치면 일괄 해소"는 절반만 참. a11y 로직이 3중복이라 먼저 composable로 통합해야 함**

### Finding (실측)
`solsol-brand/app/components/`의 모달 실체는 3개 + 인라인 1개다:

| 컴포넌트 | 성격 | 커버리지 | 키보드/포커스 로직 |
|---|---|---|---|
| `SolsolModal.vue` | 전역 싱글턴 alert/confirm(app.vue 1회 마운트) | **`useModal().alert/confirm` 30콜 / 11파일** 전부 이걸 경유 | onKeydown(Esc)+onBackdrop+초기 focus **자체 구현** |
| `TermsModal.vue` | 약관/개인정보/마케팅 3종 공용(slot 주입) | 3종 콘텐츠 | onKeydown+onBackdrop+초기 focus **복붙(거의 동일)** |
| `AccountDeleteModal.vue` | 탈퇴 전용(체크박스+비번) | 1화면 | onKeydown+onBackdrop+초기 focus **복붙(거의 동일)** |
| `signup.vue` 인라인 | `modal-card` 마크업 직접 사용 | 가입 | 별도(grep 확인) |

**"SolsolModal에 포커스 트랩 추가 시 일괄 해소" 주장의 진위:**
- **참인 부분**: alert/confirm 계열은 30콜 전부가 **단일 SolsolModal 인스턴스**를 경유한다(useModal 싱글턴). 이 한 컴포넌트에 트랩을 넣으면 그 30개 사용처가 실제로 한 번에 해소된다. 공용 컴포넌트가 "진짜 공용"인 것은 이 경로에 한해 사실이다.
- **거짓인 부분**: TermsModal·AccountDeleteModal·signup 인라인은 SolsolModal을 경유하지 않는 **독립 구현**이고, 셋은 keyboard/backdrop/focus 로직이 **복사-붙여넣기로 3중복**돼 있다(코드 비교: 세 파일의 `onKeydown`/`onBackdrop`/`onMounted focus`가 문자 단위로 거의 동일). SolsolModal 한 곳을 고쳐도 이 셋은 안 바뀐다.
- **더 심각한 사실**: 세 컴포넌트 어느 것도 **실제 focus trap(Tab 순환 가둠)을 구현하지 않는다.** 전부 초기 `.focus()` + Escape 닫기 + backdrop 클릭뿐이다(grep: `focus-trap`/`focusTrap`/`Tab` 매치 0). 즉 "포커스 트랩 추가"는 SolsolModal뿐 아니라 **4곳 전부에 신규로 넣어야 할 미구현 기능**이지, 한 곳에 이미 있는 걸 퍼뜨리는 게 아니다.

### Decision (아키텍트 결정)
**포커스 트랩·Escape·backdrop·초기 focus를 `useModalA11y()`(또는 `useFocusTrap`) composable 하나로 추출하고, 4개 모달 구현부가 전부 이걸 쓰게 리팩터한다.** 그래야 storyboard가 반복 언급하는 "한 번에 일괄 해소"가 **비로소 참이 된다.** 순서:

1. `app/composables/useModalA11y.ts` 신설: `cardRef`, `onKeydown`, `onBackdrop`, 초기 focus, **그리고 진짜 focus trap(Tab/Shift+Tab 순환 가둠)** 을 한 곳에.
2. SolsolModal·TermsModal·AccountDeleteModal·signup 인라인이 이 composable을 소비하도록 교체(3중복 제거).
3. 이후 a11y 개선은 composable 1곳 수정 = 전 모달 반영 — storyboard의 "일괄 수정" 서술이 코드 사실과 일치하게 됨.

> **근거**: 지금 storyboard 여러 문서가 "SolsolModal 고치면 11개 모달 해소"라고 적은 것은 **코드 현실을 오독한 것**이다(11 = alert/confirm 사용 파일 수이지 모달 컴포넌트 수가 아니다). 이 오독을 방치하면 "SolsolModal만 고치면 됨"이라 믿고 착수한 개발자가 TermsModal·AccountDeleteModal의 미접근성을 놓친다. composable 통합은 3중복을 제거(유지보수 부채 상환)하면서 그 서술을 사후적으로 참으로 만드는 유일한 방법이다. 규모도 작다(파일 4개, 로직 ~30줄).

## 항목 5. screenDocs.ts 매핑 아키텍처 — **결정: 수동 const+리터럴을 폐기하고 파일명 규약 기반 빌드타임 자동생성으로 전환**

### Finding (실측)
현재 `app/utils/screenDocs.ts`는 **931줄**이고 두 개의 안티패턴을 동시에 갖고 있다:

1. **거대 단일 파일 + 수동 이중 기재**: 285줄가량이 `STORY_*` const 선언, 나머지 ~600줄이 `screenDocs` 객체 리터럴 매핑. const를 선언하고(1) 다시 리터럴에서 참조(2)하는 이중 기재라 화면 하나 추가에 2곳을 편집해야 한다. 44개 규모에서 이미 931줄이면 71개 브랜드 완성 시 +, 크리에이터+브랜드 전체(수백 화면)면 수천 줄 단일 파일이 된다 — 이는 "한 파일이 너무 많은 일을 한다"는 명백한 신호.
2. **flat map을 라우팅 인덱스로 과부하**: 키에 실제 화면ID가 아닌 의사ID가 대량 섞여 있다 — `'S-AD01-0101-002·detail-order-history'`, `'S-AD01-0201-006(탭2)...'`, `'미부여-관리자-추가-모달'`, `'modal-공통-컨펌'`. 화면ID 체계(항목 1)의 규약 밖 문자열이 매핑 키로 들어와, **이 파일이 "화면ID→문서"가 아니라 "서브뷰 라우트→문서" 인덱스로 은근슬쩍 확장**됐다. storyboard 전환으로 `design`·`policy` 두 필드가 이제 **항상 동일 문서를 가리킨다**(README §4) — 즉 리터럴의 절반은 순수 중복이다.

### Decision (아키텍트 결정)
**storyboard 파일명이 이미 화면ID를 담고 있다는 사실을 정본으로 삼아, 수동 매핑을 빌드타임 글롭 자동생성으로 대체한다.** storyboard 파일명 규약(`<제품>/<화면ID>-<슬러그>.md`, README §1)이 이미 "화면ID ↔ 문서"의 single source다 — 수동 const는 그 정보를 손으로 베낀 사본일 뿐이라 정보가치가 0에 수렴한다.

1. **자동생성 스크립트**: `scripts/gen-screen-docs.mjs` — `docs/storyboard/**/<id>-<slug>.md`를 글롭해 파일명 앞부분(화면ID)을 파싱, `{ [id]: { design:[ref], policy:[ref] } }`를 생성(design·policy 동일 ref). storyboard로 이관된 제품은 이 경로로 완전 자동화 → 화면 추가 시 **파일만 만들면 매핑이 따라온다**(2곳 편집 → 0곳).
2. **제품별 파일 분리**: 자동생성 산출물을 `screenDocs.creator.ts` / `screenDocs.brand.ts`로 분리하고 `screenDocs.ts`는 얇은 병합 진입점만. 단일 931줄 파일 해소.
3. **의사ID(`·`,`(탭N)`,`미부여-`) 처리**: 서브뷰 라우트→문서 인덱스는 화면ID 매핑과 **관심사가 다르므로** 별도 테이블(`subviewDocs`)로 분리하거나, 라우트 메타에서 파생. 화면ID 맵을 라우팅 인덱스로 겸용하는 과부하를 끝낸다.
4. **과도기**: 아직 storyboard로 이관 안 된 크리에이터 사용자단(`policy/`·`design/` 유지 중, README §5)은 수동 매핑을 남기고, storyboard 이관 완료분만 자동생성으로 전환. 두 방식이 병합 진입점에서 합쳐진다.

> **근거**: storyboard 전환이 design/policy를 1:1로 수렴시킨 순간, 수동 const+리터럴은 "파일명에 이미 있는 정보를 손으로 두 번 베끼는" 순수 부채가 됐다. 71개면 참을 만할지 몰라도 크리에이터+브랜드 전체에서는 수천 줄 수동 매핑이 되고, 편집 2곳 규칙 때문에 drift(스테일 매핑 — `:508~510`·`:525`에서 이미 관측됨)가 필연이다. 파일명 규약이 정본이면 코드는 그걸 읽기만 하면 된다. 이건 "나중에 검토"가 아니라 **이관이 더 진행되기 전에(파일이 적을 때) 전환하는 게 정확히 지금** 유리한 결정이다.
