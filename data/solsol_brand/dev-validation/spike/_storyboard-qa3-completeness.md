# storyboard(solsol-brand) 완결성 감사 — 3차 검수, 신규 페르소나(Completeness Critic)

- **역할**: 도담(qa) — 이번 라운드 신규 투입 "완결성 감사(Completeness Critic)". 개별 파일 정확성이 아니라 **45개 세트 자체가 충분한가**를 감사.
- **대상**: `docs/storyboard/solsol-brand/`(45개 파일, 실질 화면ID 문서 44개 + 폐기예고 요약 1개)
- **대조 기준**: `docs/dev-validation/spike/br01-r04.md`(26건 결함 원장 + §8 후속정정) · `docs/validation_modified/BR01_화면ID_매핑표.md`(§2~§4, §6) · `app/utils/screenDocs.ts`
- **주의(감사 중 관측)**: 감사 도중 `S-BR01-0301-002_pu01` 문서의 `[미확정]` 태그가 다른 세션(3차 UX 후속검증 페르소나로 추정)에 의해 실시간으로 `[확정]`으로 정정되는 것을 목격했다 — **여러 페르소나가 같은 폴더를 동시 편집 중**이다. 아래 수치는 조사 시점(그 정정 반영 후) 스냅샷이며, 이 보고서 완성 시점과 실제 파일 상태 사이에 추가 드리프트가 있을 수 있다.

## 1. 커버리지 갭

### 1-A. br01-r04(26건 결함) 대비

26건 결함 중 storyboard가 다루는 화면은 **누락 없이 커버됨**. 특히:
- D14(에러 화면 4건 ID 스왑 주석)는 4개 파일(9001-001/002/004/005) 전건에 정확히 반영됨.
- br01-r04 §8 후속정정 2건(도메인 중복확인 모달 mock→실연동, 구독취소 mock→실연동)도 해당 파일에 반영 확인.

다만 **결함이 아니라 "화면" 단위로 보면 갭이 있다** — D02(blocker, `/purchase` 계열 진입 플로우)가 참조하는 인접 화면 중 `S-BR01-0601-003`(구매완료, `/purchase-complete`)·`S-BR01-0601-005`(구매실패, `/purchase-failed`)·`S-BR01-0601-008`(purchase-login, 고아)는 **storyboard 문서가 없다**. D02 자체의 진입점(`/purchase`=0601-002)은 문서화되어 있으나, blocker 정상화 작업을 하려는 개발자가 참조할 인접 플로우 3개 화면은 빠져 있다 — 결함ID 매칭 관점에서는 "커버됨"이지만 화면 플로우 관점에서는 실무 공백.

### 1-B. 매핑표(§2~§4, §6) 대비 — 71개 화면ID 우주 기준

`BR01_화면ID_매핑표.md`가 정의하는 전체 화면ID는 **71개**(본화면 39+레거시6+모달6+레거시모달1=52, 07-27 §6 재배정으로 +7 알럿/컨펌 +12 이메일 = 71). storyboard 44개 문서가 커버하는 ID는 **44개**, 미커버 **27개**.

- **경계 기준 확인**: `app/utils/screenDocs.ts:78` 주석 "br01-r04 재검증 우선순위 25화면"과 §6(2026-07-27 오너 재승인) 19건(알럿·컨펌 7 + 이메일 12)을 더하면 25+19=**44** — storyboard 44개와 정확히 일치한다. 즉 이번 배치의 실제 스코프는 "25화면 우선순위 배치" + "07-27 오너 재승인 19건" **두 결정의 합집합**이며, 산술적으로는 이 44개가 의도된 스코프임이 맞아떨어진다.
- **그러나 결정적 문제**: 71개 우주 중 어떤 27개가 "이번 배치 제외 대상"인지 **열거된 목록이 어디에도 없다**. `screenDocs.ts:78` 주석은 "25화면"이라는 **개수**만 적었을 뿐 화면ID를 나열하지 않았고, 매핑표 §6도 "19건 재배정"만 다룰 뿐 미포함 27건을 명시하지 않는다. 이번 감사에서 27건 목록은 **71 - 44 차집합을 직접 계산해서만** 얻을 수 있었다 — 이는 "의도적 제외"와 "실수 누락"을 사후적으로 구분할 근거 문서가 실질적으로 없다는 뜻이다(§2 원 질문에 대한 답 = **아니오, 없음**).
- **미커버 27건**:
  | 구분 | 화면ID | 비고 |
  |---|---|---|
  | 본화면(18) | 0101-001(홈), 0301-002(가입약관), 0301-003(가입완료), 0302-002(비번찾기), 0302-005(비번재설정발송), 0401-001(사이트만들기 본문), 0601-003(구매완료), 0601-005(구매실패), 0601-006(홈pricing), 0601-008(purchase-login), 0701-002(문의완료), 0901-001(계정관리 본문), 1101-001~005(약관4종+마케팅동의), 9001-003(네트워크에러) | |
  | 레거시(6) | 0102-001·0103-001(실앱 직접구현·해소됨)·0104-001·0105-001(실사이트 대체)·0501-001·0501-002(won't-fix) | 매핑표가 "해소/대체/won't-fix"로 이미 처리 — storyboard 미작성이 정당 |
  | 모달(2) | 0302-003_pu01(비번재설정완료 모달), C01(약관/개인정보/마케팅 공유 모달) | |
  | 레거시모달(1) | 0801-001_pu01(구독취소완료, 구넘버링) | 신규ID(0801-003_pu01)로 대체됐으나 §6.4가 "관계 미확정"이라 명시 — 매핑표 스스로도 이 ID의 최종 운명을 확정 못한 상태 |

  레거시 6건 + 이미 처리된 항목 제외 시 **실질적으로 "설명 없이 빠진" 화면은 약 20건**(본화면 18 + 모달 2). 이 중 `0901-001`(계정관리 본문)·`0401-001`(사이트만들기 본문)은 **자식 모달은 이미 5개나 문서화됐는데 부모 페이지 자체가 없는** 기이한 패턴 — 카드 삭제/등록 확인 모달을 이해하려는 사람이 정작 그 모달이 뜨는 부모 화면 문서를 못 찾는다.

### 1-C. 검증 깊이 갭 (신규 발견 — 커버리지 갭과는 다른 종류)

이메일 템플릿 12건 중 `S-BR01-1201-001`(비번재설정)·`S-BR01-1201-002`(가입인증코드) 2건만 "brand-api 발송 TODO 잔존(D17 근거 `auth.ts`)"을 명시했다. 나머지 10건(결제완료·결제실패·결제유예·서비스생성·서비스중지·서비스중단·사용량경고·구독취소·만료도래·만료)은 **"언제 발송되는가"만 서술하고 "실제로 발송 로직이 구현됐는지"는 검증하지 않았다** — 이 10건의 트리거는 `subscriptions.ts`/`payments.ts` 등 auth.ts 밖의 다른 라우트일 가능성이 높아 D17(auth.ts 근거)이 그대로 적용된다고 단정할 수 없다. **화면(이메일) 존재는 44/44 커버됐지만, 발송 구현 여부라는 실질 위험은 12건 중 2건만 실측됐다** — "커버리지 100%"와 "검증 완료"를 혼동하면 안 되는 사례.

### 표B — 이미 승인/확정됐으나 카테고리 라벨로 남아있는 항목 (참고, 9건 이상)

`오너 확인(금전/결제)`·`오너 확인(결제수단)`·`오너 확인(계정/보안)`·`오너 확인(비가역·금전 인접)` 형태의 **bare 태그**는 "필요"·"대기"가 붙지 않고, 문맥상 이미 승인된 정책/구현을 가리키는 참조 라벨로 쓰인다(예: `S-BR01-0601-004`·`0601-002`·`0801-001`·`0801-002`·`0901-001_pu01`·`0901-001_pu02`·`0801-003_pu01`·`0302-001`(GA 전 OFF 재배포 체크리스트)·`0901-002`). 실행 시점 액션(예: GA 전 재배포)은 있지만 **오너가 새로 판단할 내용은 없음** — 표A와 혼동하지 않도록 분리했다.

**총 태그 인스턴스 = 표A 29(+조건부1) + 표B 9 이상 ≈ 39건.** "오너가 결정해야 할" 순수 미결 항목은 **29건**이며, 이 중 어디에도 **하나로 총괄된 목록이 없었다**(각 파일에 흩어져 있었음) — 이번 감사로 처음 취합됨. 오너가 45개 파일을 개별로 다 읽지 않는 한 이 29건 중 다수(특히 이메일 15건)를 놓칠 위험이 실재한다.

## 4. 버전/이력 관리

- 44개 파일 헤더(`> route: ... · 최종수정 YYYY-MM-DD`)는 **전부 2026-07-27 단일 날짜**로만 찍혀 있어, 헤더만 봐서는 이 파일이 1차 작성 후 그대로인지 2차·3차 수정을 거쳤는지 **구분이 안 된다**.
- 본문 grep 기준 **18개 파일**이 "N차 QA"·"N차 UX" 형태의 인라인 정정 각주를 갖고 있다(최소 2차, 다수 3차) — 즉 44개 중 40% 이상이 이미 2회 이상 수정을 거쳤다.
- 정정이 정정을 참조하는 사례도 나타난다: `S-BR01-1201-002`는 "3차 QA — 이전 초안이 무관한 항목을 잘못 인용했으나" 식으로 **2차 정정의 오류를 3차가 다시 정정**하고 있다. `S-BR01-0801-001`도 "이전 버전은 ... 오기재였다"로 동일 패턴.
- **위험**: 현재 관례는 인라인 각주 누적형(`**[정정 YYYY-MM-DD]**` 텍스트를 본문에 계속 追加)이라, 라운드가 늘수록 한 파일 안에 "구 진술 취소선 + 정정 진술 + 그 정정에 대한 재정정"이 계속 쌓인다. 지금은 2~3차라 아직 읽을 만하지만, 4차·5차가 이어지면 **본문과 정정 이력이 뒤섞여 어느 게 최종 사실인지 파악하기 어려워질 위험**이 있다. 허브의 다른 정본들(`docs/history/`처럼 날짜별 append-only 로그, 또는 `docs/dev-validation/spike/br01-r04.md` §8처럼 "후속 정정" 전용 섹션 분리)과 달리, storyboard는 **정정 전용 섹션이 없어 본문 불릿 사이사이에 정정이 섞여 들어간다**.
- **제안**: 파일 템플릿(`docs/storyboard/README.md` §2)에 "## 정정 이력" 전용 절을 추가하고, 본문은 항상 최신 확정 사실만 유지 + 정정 이력은 그 절에 append하는 방식을 권장(허브 `history/` 관례와 정합). 지금 되돌리기엔 44개 파일 전수 리팩터 비용이 크므로, **당장 강제하기보다 다음 라운드(4차)부터 적용 권고**로 남긴다.

## 5. 개선 제안

1. **매핑표 27건 제외 목록을 명시적으로 문서화**: `screenDocs.ts` 주석 또는 매핑표에 "이번 44개 배치에서 제외된 27개 화면ID와 그 사유(레거시/저우선/후속예정)"를 표로 한 번은 박아둘 것. 지금은 71-44 차집합을 계산해야만 알 수 있다.
2. **D02 인접 3화면(0601-003·005·008) storyboard 보강**: blocker와 직접 연관된 인접 플로우이므로 우선순위를 25화면 원안보다 올려서 다음 배치에 포함 권고.
3. **오너 확인 대기 29건(표A) 총괄 전달**: 이번 문서가 그 역할을 함 — 총괄이 오너에게 한 번에 전달하고, 파일별 산개 상태는 그대로 두되 이 문서를 "인덱스"로 링크해둘 것.
4. **이메일 발송 구현 여부 10건 재검증**(§1-C): `auth.ts` 밖 라우트(`subscriptions.ts`·`payments.ts` 등)에 실제 발송 로직이 있는지 별도 확인 필요 — D17이 auth.ts 2건에만 근거하고 있어 나머지 10건은 미검증 상태로 남아있다.
5. **횡단 결함 색인**: `br01-r04.md`에 "결함ID → 영향 화면 수·목록" 요약표 1개 추가(storyboard 쪽 개별기록 원칙은 유지, 원장 쪽에만 가벼운 색인 추가).
6. **정정 이력 전용 섹션** 도입(§4) — 다음 라운드부터 권고.
7. **동시편집 관측**: 이 감사 중 다른 페르소나의 실시간 수정을 목격했다(상단 주의 참조) — storyboard 폴더가 아직 git 미추적(`?? docs/storyboard`)이라 충돌 시 롤백 지점이 없다. 다음 커밋 시점에 스냅샷을 잡아두는 것을 권고.
