### 2-3. C-3 신규 발견 — `S-BR01-0302-001`(로그인) storyboard의 비밀번호 문구 취급 공백

- `05_정책설계서.md` §C-3 원문이 **"Brand 로그인폼 placeholder만 구버전 문구 '8자 이상'으로 잔존"** 이라고 BR01 로그인 화면을 콕 집어 지적했음에도, storyboard `S-BR01-0302-001-로그인.md`의 "정책(변경 사항·값·수치)" 섹션은 이 사안을 **전혀 언급하지 않는다**(게스트 게이트·검수계정만 서술).
- 반면 같은 축의 다른 화면들은 이미 정확히 다루고 있음: `S-BR01-0301-001-회원가입.md`("비밀번호 규칙: 8~16자, 영문·숫자·특수문자 조합 필수"), `S-BR01-0302-003-새-비밀번호-설정.md`(동일, "05_정책설계서 확정" 각주까지 포함) — **일관성 결여**: 같은 C-3 사안을 어떤 화면은 정확히 다루고, 정작 C-3 원문이 지목한 화면(로그인)은 침묵.
- **더 중요한 사실**: 이 정확한 사안이 이미 `docs/dev-validation/mockup/br01-r01.md` **D03**(2026-07-09, 중 등급)으로 원장에 등재되어 있고 **여전히 open**이다 — "비번 placeholder 3파일 3문구: login '8자 이상'(상한없음)·signup/account '최소 8자 특수문자'·reset-new '8~16자 조합'"으로 이미 정확히 기술됨. 즉 신규 결함은 아니고 **기존 blocker가 storyboard 문서에 인용 누락**된 것 — 1201-002와 같은 성격(확정/기존 사실의 인용 누락)이나, 이번엔 정책 오분류가 아니라 **문서 간 교차참조 누락**이다.
- **권고**: `S-BR01-0302-001-로그인.md` 정책 섹션에 "비밀번호 placeholder 구버전 문구 잔존(`login.html:34` '8자 이상' — `05_정책설계서.md C-3` 확정값 '영문·숫자·특수문자 3종 8~16자'로 교체 필요, 원장 `br01-r01-D03` open 참조)" 각주 추가 권고. `[→ 나래님]` 문서 보강, `[→ 브랜드 세션]` 실 코드(login.html/mockup2, 이후 app/pages 이식본) 교체는 D03 원장 담당 그대로 유지.

## 3. `S-BR01-0601-007` 카드등록 정책 공백 재평가

**재평가 결론: 낮은 위험 — "상위 정본과의 충돌"이 아니라 "신규 설계 문서 미작성" 유형.** 개발 착수를 막을 blocker는 아니나, 금전 접점이라 P0 오픈 전 문서화는 필요.

**근거**:
1. `05_정책설계서.md` M-8(PG 빌링키·토큰·환불 흐름)이 결제 골격 전반(§4·§7)을 이미 채택했지만, **카드 "등록" UI 자체의 정책(SDK 위젯 채택 여부·필수 입력값·기본카드 지정 규칙)은 M-8 범위에 없다** — M-8은 웹훅/서명검증/재시도/멱등 등 결제 처리 파이프라인에 집중, 카드 등록 폼의 UI 정책은 다루지 않음. 즉 **상위 정본과 상충하는 부분이 없다**(단지 존재하지 않을 뿐).
2. storyboard 자체가 이미 안전장치를 갖추고 있음: staging 게이트로 실 SDK 미호출 명시, "무음 성공 위장 금지" 안내 노출, `MockBadge` 분기 — 실제 카드 승인이 일어나지 않는 현재 상태에서는 **정책 공백이 곧바로 사고로 이어지는 구조가 아니다**.
3. 다만 실 토스페이먼츠 SDK 연동 단계(스텁 입력폼 유지 vs SDK 위젯 교체)로 넘어가는 순간 **정책 결정 없이 구현이 먼저 진행될 위험**이 있다 — 이 갈림길에서 정책 문서 부재가 실질적 리스크가 된다(현재는 아니고, 다음 단계 진입 시점이 위험 시점).

**권고 — 정책 초안 골자(문서 작성은 하지 않음, 골자 제안만)**:
- **결정 필요 사항 1**: 카드 등록 UI를 자체 폼(카드사/타입/뒤4자리 스텁 유지) vs 토스페이먼츠 SDK 위젯(iframe) 중 무엇으로 갈지 — PCI-DSS 범위 회피 관점에서는 SDK 위젯이 유리(카드 원본 정보가 자사 서버를 거치지 않음), 반면 자체 폼은 UX 커스터마이징이 쉬움.
- **결정 필요 사항 2**: 대표카드 지정 규칙 — 이미 `S-BR01-0901-001_pu01~04`(대표카드 등록/삭제/최소1개/삭제불가 확인)에 규칙이 산재해 있으므로, 카드등록 정책 문서는 이 4개 모달의 규칙을 등록 시점 관점에서 **재인용·정합**해야 함(신규 규칙 발명 아님).
- **결정 필요 사항 3**: 필수 입력값 확정(카드사 목록 9개사 고정 여부·체크/신용 구분 필요 여부).
- **결정 필요 사항 4**: staging 게이트 해제 조건(운영자 컨펌 항목으로 명문화) — M-8 "실결제·실환불 자동화는 비가역, staging 선검증·운영자 확인 전제" 원칙을 카드 등록에도 동일 적용한다는 문장만 있으면 충분.
- **제안 위임**: `[→ 오너]` 카드등록 정책 문서 신설 필요성 자체는 최종 판단(2차 발견4 위임과 동일) — 단, **"실 SDK 연동 착수 시점 이전에" 라는 트리거 조건**을 붙여 우선순위를 명확히 할 것을 권고(지금 당장 급하지 않음).
