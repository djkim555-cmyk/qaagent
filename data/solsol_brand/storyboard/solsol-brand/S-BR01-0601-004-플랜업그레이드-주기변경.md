# [S-BR01-0601-004] 플랜 업그레이드/주기 변경
> route: /my/product-upgrade-cycle · 정리: 나래님 · 최종수정 2026-07-27 (KST) · 상태: 작성완료

## 기능 정의
- 현재 구독 중인 플랜을 상위 플랜으로 업그레이드하거나 구독 주기(월간↔연간)를 변경하는 화면. "선택된 플랜" 요약(현재 플랜명·사이트명·"현재 이용중"·구독 주기·구독 기간·다음 결제일) + "플랜 업그레이드 선택"(플랜탭 + 월간/연간 토글) + 결제 예정 금액(비례정산 견적) + 결제 금액 요약(구독 요금·현재 구독 미사용 금액(일할)·산정된 결제 금액) + 업그레이드 혜택 안내 + 결제하기.
- 쿼리: `subscriptionId`(필수 — `my/sites.vue`의 "플랜 업그레이드" 버튼이 전달).
- 업그레이드 대상은 현재 플랜보다 단가가 같거나 높은 플랜만(다운그레이드 제외, free 제외).
- 비례정산(proration) 견적 EP는 brand-api에 없음(스파이크 미비계약) — 이 화면은 목업2와 동일 방식(잔여기간 일할 계산)을 클라이언트에서 계산하고 `MockBadge`("비례정산 견적(확정 아님)")로 표기. 실제 정산·차액결제는 `PATCH /api/subscriptions/:id/plan`(⚠️게이트) 응답이 `gated:true`인 staging-gate — 서버는 플랜/단가만 교체하고 실 토스 차액 승인은 하지 않음.

## 표시 조건 · 상태·분기
- 로딩/에러/변경 가능한 플랜 없음(empty) 3분기.
- 현재 이용 중인 플랜·주기와 동일한 조합 선택 시(`isCurrentSelection`) 결제 버튼에 "변경 사항이 없어요" 표시 + 비활성, "현재 {플랜명}·{주기}을 이용 중입니다. 상향(업그레이드) 시에만 결제가 진행돼요" 안내 노출.
- 월간·연간 토글은 항상 클릭 가능(과거: 현재 조합과 같은 플랜의 월간 비활성 → 현재: 클릭 가능하되 현재 조합 선택 시 결제만 불가) — 정책문서 §표시조건과 정합.
- 결제 버튼 비활성 조건: 현재 조합 선택 중이거나, 플랜 미선택, 카드 미선택, 약관 미동의 중 하나라도 해당.

## 정책 (변경 사항 · 값·수치)
- **오너 확인(금전/결제)** — 정본: `docs/policy/brand/front/pricing-upgrade.md`(§플랜 업그레이드 — 결제 금액 산정, 클로드 구독제식 비례정산).
- **전제**: 현재 구독 = Basic 월간(정책문서 예시 기준, 실연동은 서버가 반환하는 실제 구독으로 대체). **상향(업그레이드)만 가능.**
- 산정 금액(VAT별도) = **새 플랜 청구액 − (현재 월간가 × 잔여비율)**. 결제 예정 금액(VAT포함) = 산정 금액 × **1.1**(VAT 10%). 새 플랜 청구액 = 월간이면 월가, 연간이면 연가(월환산가×12).
- **잔여비율(일할 계산)** = 현재 청구주기 잔여일 ÷ 총일(청구 앵커일 14일 기준, 실연동은 `subscription.currentPeriodStart`~`currentPeriodEnd` 기준으로 대체). "다음 결제일"도 앵커일로 동적 표기.
- 표시 조건(상향만 가능): Free=비활성(다운그레이드 불가) / Basic+월간=현재 조합이면 "현재 이용 중인 플랜" 표기·산정/결제 예정 0원·결제하기 비활성·안내 문구 / Basic 연간·Growth·Advanced(월간·연간)=상향이면 비례정산 후 결제 활성(약관 동의 시).
- 값·수치: VAT 10%, 청구 앵커일 14, 연간 할인 30%. 가격은 `S-BR01-0601-001` 정본표 참조.
- 검증 예(잔여 6/30일=크레딧 20,000): Growth 월간 280,000/308,000 · Growth 연간 2,500,000/2,750,000 · Advanced 월간 480,000/528,000 · Basic 연간 820,000/902,000.

## 이식 주의 종합
- '구독서비스 결제 안내' 블록 누락은 `product-pay-now`와 **2화면 공통**(자동연장은 대상 아님, 정정됨). 플랜 등급 배지 누락은 `product-auto-renew`·`product-pay-now`와 **3화면 공통** — 개별 수정보다 일괄 이식 권장(단 두 결함의 공통 범위가 다름에 유의).
- 비례정산 산식은 오너 확인된 금전 정책이므로, 실 서버 견적 EP 신설 전까지 임의로 산식을 바꾸지 말 것.
- 카드 등록 완료 여부로 결제 버튼 활성 조건이 결정되므로, `CheckoutCardBox` 연동 상태와 함께 검증할 것.
- **처리 순서(2026-07-27 3차 UX 후속검증 추가, 2차 QA "blocker 없는 화면 우선순위 부재" 해소)**: 이 화면은 blocker(상)가 없고 중 2건·하 1건이 병렬 나열돼 있었으나 착수 순서를 명시한다 — ① **중** 계약 갭(비례정산 견적 MOCK) 확인부터: 서버 견적 EP 신설 여부를 오너/개발 리드에 먼저 확정한다(이 화면 신뢰성의 근본 전제이자, 확정 결과에 따라 이후 마크업 작업의 우선순위도 달라질 수 있음) → ② **중** `checkout__notice` 블록 복원(`product-pay-now`와 동시 처리, 즉시 착수 가능한 저비용 작업이라 나중에 해도 리스크 없음) → ③ **하** 플랜 등급 배지 복원(`product-auto-renew`·`product-pay-now`와 동시 처리).
